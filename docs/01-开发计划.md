## 二、技术选型

| 项 | 选型 | 理由 |
|---|---|---|
| 运行时 | .NET 8（`net8.0` / `net8.0-android`） | **LTS，支持到 2026-11**；.NET 9 是标准期限版本（STS）。`global.json` 固定到 8.0.425，构建可复现 |
| UI | Avalonia 11.3.x + FluentAvaloniaUI | 与 QRKeeper 同版本线，样式资产可平移 |
| MVVM | CommunityToolkit.Mvvm 8.4（source generator） | `[ObservableProperty]` / `[RelayCommand]`，无运行时反射，利于 Android 裁剪 |
| DI | Microsoft.Extensions.DependencyInjection | 与 QRKeeper 一致 |
| 只读成分库访问 | **Microsoft.Data.Sqlite 直连 + 手写 SQL** | 44,401 食物 / 183 万营养值，EF Core 物化开销与启动成本不划算；且 Android AOT 下 EF 反射裁剪风险高 |
| 用户数据库访问 | **EF Core 9 + Sqlite** | 用户/收藏/餐食/查询历史是典型小型关系模型，需要迁移能力 |
| 图像处理 | SkiaSharp（Avalonia 自带）+ 平台图片选择器 | 拍照/相册统一走 `IImagePickerService` 平台实现 |
| 在线 HTTP | `HttpClient` + `System.Text.Json`，统一 `IHttpClientFactory` 风格封装 | 便于加超时、重试、缓存与降级 |
| 测试 | xUnit + FluentAssertions | 覆盖搜索、归一化、建议引擎、导入导出 |

> **双 ORM 是刻意设计**：只读大数据走裸 SQL（快、可裁剪），可写小数据走 EF Core（迁移方便）。两者共用同一个 SQLite 连接工厂与事务边界。

## 四、数据方案

### 4.1 为什么必须重建派生库

原始库有三个问题无法直接在 App 内消化：

1. **营养素没有归一化**。`canonical_key` 是 `数据集:原字段名`，中国是 `fitness.food.nutrient:热量`，台湾是 `taiwan_fda_food_composition:一般成分:热量`，日本是 `Main table:ENERC_KCAL`，美国是 `food_nutrient:1008`。不归一化就无法跨库对比、无法算营养目标达成率。
2. **长表结构不适合列表渲染**。每页 20 条列表若逐条 `join nutrient_value`（183 万行），移动端会明显卡顿。
3. **体积**。500 MB 无法进 Android。

### 4.2 派生库 Schema（两库同构，仅行数不同）

```sql
CREATE TABLE food (
  food_id INTEGER PRIMARY KEY,
  name TEXT NOT NULL,             -- 简体规范名
  name_original TEXT,
  search_text TEXT NOT NULL,      -- 归一化检索串（简繁统一、去标点、附拼音首字母）
  group_key TEXT NOT NULL,        -- 14 类统一分类
  group_display TEXT,             -- 原始分组名（中文优先）
  source_key TEXT NOT NULL, source_display TEXT NOT NULL,
  source_food_id TEXT,
  edible_pct REAL, region TEXT, description TEXT,
  -- 冗余常用列：列表页/排序/筛选免 join
  energy_kcal REAL, protein_g REAL, fat_g REAL, carb_g REAL,
  fiber_g REAL, sugar_g REAL, sodium_mg REAL, potassium_mg REAL,
  calcium_mg REAL, cholesterol_mg REAL,
  external_url TEXT               -- 中国平台 foodinfo/{id}.html
);
CREATE TABLE nutrient_catalog (
  key TEXT PRIMARY KEY, name_cn TEXT, name_en TEXT, unit TEXT,
  category TEXT, sort INTEGER, ref_daily REAL
);
CREATE TABLE food_nutrient (
  food_id INTEGER, nutrient_key TEXT, amount REAL, unit TEXT,
  PRIMARY KEY (food_id, nutrient_key)
);
CREATE VIRTUAL TABLE food_fts USING fts5(name, search_text, tokenize='unicode61');
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT);  -- schema_version / built_at / source_sha256 / scope
```

### 4.3 规范营养素（41 项）

能量、水分、蛋白质、脂肪、饱和脂肪、单不饱和脂肪、多不饱和脂肪、反式脂肪、胆固醇、碳水化合物、糖、膳食纤维、灰分、钠、钾、钙、镁、磷、铁、锌、铜、锰、硒、碘、维生素 A(RAE)、视黄醇、β-胡萝卜素、维生素 D、维生素 E、维生素 K、硫胺素 B1、核黄素 B2、烟酸、泛酸、维生素 B6、生物素、叶酸、维生素 B12、维生素 C、胆碱、咖啡因、酒精。

统一单位：能量 kcal（kJ 换算 ÷4.184），宏量 g，矿物质 mg（μg ÷1000），维生素 μg 或 mg 按项固定。

### 4.4 两个库的范围

| 库 | 数据集 | 食物数 | 估计体积 | 用途 |
|---|---|---|---|---|
| `food_full.db` | 全部 16 个（USDA 3 + 日本 12 + 中国 + 台湾） | 44,401 | 约 120–150 MB | Windows 完整版 |
| `food_core.db` | 中国(15) + 台湾(16) + 日本主表(4) | 6,198 | 约 20–25 MB | Android 内置；Windows 回退 |

> 说明：体积比原始库小很多，因为只保留 41 个规范营养素（原始 941 条定义里大量是氨基酸/脂肪酸细分项），且统一为短表结构。桌面版保留全量食物但同样做营养素收敛——需要细分项时再回原始库查（`food_full.db` 保留 `source_food_id` 可回溯）。

### 4.5 分类归一化（14 类）

`谷物薯类 / 豆类及制品 / 蔬菜 / 水果 / 畜禽肉 / 水产 / 蛋类 / 奶类 / 坚果种子 / 油脂 / 糕点甜食 / 饮料 / 调味品 / 加工食品`，另设 `其他`。
映射表覆盖中/繁/英/日四种原始分组名，未命中归 `其他` 并记入构建日志（可人工补表）。

### 4.6 中国平台链接映射

`link_china.py` 对 `food_core.db` 中 1,447 条中国食物逐条调用：

```
POST https://nlc.chinanutri.cn/fq/FoodInfoQueryAction!queryFoodInfoList.do
body: categoryOne=0&categoryTwo=0&foodName={name}&pageNum=1&field=foodName&flag=1
```

返回 `list[0]` 即记录 id → `https://nlc.chinanutri.cn/fq/foodinfo/{id}.html`。
策略：名称完全匹配优先，否则取首条并把匹配度写入 `meta`；请求间隔 300 ms，失败重试 2 次，结果缓存到 `data/generated/china_links.json` 避免重复抓取。

## 五、建议引擎设计

三层，全部离线，无大模型依赖：

1. **目标层 `TargetCalculator`**
    Mifflin-St Jeor 算 BMR → 按活动系数得 TDEE → 按目标（维持/减脂/增肌）调整 → 得到每日能量目标；再由 DRI 表（性别/年龄段/孕期哺乳期）查得蛋白质、钙、铁、锌、硒、碘、VA、VD、VE、VC、B1/B2/烟酸、叶酸、B12 的 RNI/AI，以及慢病上限（钠 2000 mg、添加糖 25 g、饱和脂肪 <10%E、胆固醇 <300 mg）。

2. **规则层 `IAdviceRule`**（可组合、可单测）
   | 规则 | 触发 | 输出 |
   |---|---|---|
   | 能量密度规则 | kcal/100g 高于阈值 | 建议份量下调 + 说明 |
   | 蛋白质贡献规则 | 每 100 g 蛋白 ≥10 g | 增肌/老年肌少风险加分 |
   | 高钠警示 | 一份占日限 >30% | 高血压/肾病用户升为「避免」 |
   | 高钾警示 | 一份 K >500 mg | 慢性肾病用户警示 |
   | 高磷警示 | 一份 P >300 mg | 肾病用户警示 |
   | 嘌呤风险 | 水产/内脏/浓肉汤 + 高蛋白 | 痛风/高尿酸警示 |
   | 饱和脂肪/胆固醇 | 占日限比例 | 高血脂/心血管警示 |
   | 添加糖/升糖负荷 | 糖、碳水构成 | 糖尿病用户份量约束 |
   | 麸质 / 乳糖 | 名称与分类特征 | 麸质敏感 / 乳糖不耐替换建议 |
   | 过敏原 | 八大类过敏原关键字 | 命中即「禁止」级 |
   | 适宜性加分 | 高纤维/高钙/富铁+VC | 「推荐」理由 |
   每条规则输出 `(Severity, Title, Detail, Basis)`，`Basis` 写清依据（如「按 DRIs 2023 成年男性钠 AI 1500 mg」），保证建议可解释。

3. **份量层 `PortionAdvisor`**
   以「一份 = 该食物常见食部重量」为基准（谷物 50 g / 蔬菜 100 g / 水果 100 g / 肉 75 g / 奶 250 ml），再用能量与限制项修正，输出 `建议 80 g`、`约 1 小碗` 双单位表述。

**免责声明**：所有建议页固定展示「本建议基于公开膳食参考摄入量推算，不构成医疗诊断或治疗建议；有明确疾病请遵医嘱」。

### W6.7 返回记录页不刷新（缺陷修复）
用户反馈：记录页「今天还差什么」里点推荐食物 → 详情页「加入今天餐饮」→ 按「返回」，
记录页的餐次明细没变；要切到别的页再切回来、或切一次日期才看得到。

原因不是数据没写进去，而是**页面对象被缓存复用**：`MainViewModel.GoBack()` 只是把
栈里的那个 ViewModel 弹回来，从没通知它重新读库。`PushAsync` 会调 `LoadAsync`，
返回这条路却没有对应的一步，所以页面停在离开时的样子。

修法：新增 `IPageActivation` 契约，返回时若目标页实现它就调用一次 `OnActivatedAsync`。
不做成基类虚方法，是因为多数页面只在首次进入时读库，无条件重载既多查一次库，
也会把用户翻到的位置重建一遍。目前 `TrackerViewModel`（详情页加餐）与
`FavoritesViewModel`（详情页取消收藏）实现了它。

顺带把「已加入今天餐饮」的提示补上日期：记录页可能正停在别的日期，只写
「已加入午餐」会让人以为没生效。真实点击路径已进 `DevShot` 的 `tracker-add`
回归路径：`返回后记录数 6 → 7：已刷新`。

实现要点：

1. **来源接口只做最窄的一件事**：关键字 → 一批条目。超时、并发、去重、失败兜底全部收在聚合器里。否则每接一个新源都要在最慢那步重写一遍同样的容错代码，各源行为还不一致，出问题只能一个个猜
2. **每个来源都必须留下一条状态**，失败也要有（`OnlineSourceState` 六态：有结果 / 无结果 / 超时 / 失败 / 未配置 / 已关闭）。界面只有拿到这个才能解释「为什么只出来两个源」
3. **超时用「取消」实现**，靠外层令牌是否被触发了来区分 `Timeout` 与用户取消。取消必须原样抛出，不能被 `catch (Exception)` 收成「请求失败」
4. **去重键：有条例码用条码，没有则「品牌 + 归一化名称」**。括号内容先去掉（「苹果(均值)」＝「苹果」）；带品牌的条目只在同品牌内合并（伊利和蒙牛的「纯牛奶」是两个商品，混成一条等于造一个谁都对不上的数字）
5. **不跨语言合并**。「Apple」与「苹果」是不是同一条得靠人判断，机器硬猜会张冠李戴（雪梨 / pear / 梨 这类尤其容易错）
6. **在线条目的字段与 `FoodSummary` 摘要列一一对应**，单位统一每 100 g（源那边是每份口径的，由来源自己换算）。这样在线结果与离线结果能用同一版卡片渲染，不需要两套模板
7. **聚合器在零来源时返回空结果而不抛错**，界面可以先做起来，T7.2 接上源就自动有数据
8. **USDA 的数值按 nutrientId 取，不按名称匹配**（E29）；先查通用库，没命中才退到商品库
9. **两个源的 `_100g` 单位口径不同**：USDA 的钠给 mg、偶尔给 g；OFF 的矿物质一律是 g（钠 `0.0428` = 42.8 mg）。不换算就会显示成 0（E30）
10. **真实响应是做解析的唯一依据**：夹具按实际响应裁（`foods/search` 的扁平结构与 `food/{id}` 的嵌套结构完全不同），不按文档想象

T7.3 / T7.4 补充要点（2026-10-22）：

11. **离线与在线是两条并行的线，谁也不等谁**。离线几百毫秒出结果，在线逐源上屏；`StreamAsync` 返回「完成顺序」，而 `SearchAsync` 会把结果按来源优先级重排——一次性结果不能因为网络快慢而换顺序（E35）
12. **缓存的目的是省时与省配额，不是省流量**。DEMO_KEY 只有 30 次/小时，缓存是最直接的配额保护；空结果一律不落库（一条 7 天前的「无结果」会挡住用户重试）
13. **「离线库已有」比「在线再查一遍」更有用**。中文食物绝大多数离线库都覆盖了，`FindExistingNamesAsync` 只做归一化同名匹配（去括号、全半角），不做模糊匹配——「苹果汁」不是「苹果」
14. **在线这一路的失败必须只影响它自己**：`_onlineGeneration` 代次号让旧任务的回写失效（取消是协作式的，光靠 `CancellationToken` 会漏一次回写），失败/超时只改自己那一格 chip

T7.5 + 本轮缺陷修复的补充要点（2026-10-22）：

15. **刷新要能只刷一个源**。三源同时重跑，等于让本来正常的两个源白挨一次请求（中文源是公益站点，无谓请求要省）。做法是每个来源一行状态（`OnlineSourceStatusRow`）各带一个刷新按钮，走新增的 `SearchSourceAsync(key)`——它复用 `StreamAsync` 那套超时/缓存/状态归纳，不另写一份逻辑。结果回来只替换该源那一组，其它源的行不动，滚动位置也不会跳
16. **在线条目要能用，就得先变成有 `FoodId` 的本地记录**。两条路：给所有下游功能加「可能没有 FoodId」的分支，或把在线条目补录成一条本地记录。选后者——改动集中在一个存储层。「补录」的边界是硬的：只写 `user.db`（`local_foods`，schema 6），**从不写 `food_full.db`**；id 取负数，让「权威离线数据」与「本机补录」共用一个 id 空间也能一眼分开；记住来源（`SourceKey` + `RemoteId` + 显示名），卡片标「在线补录 · 中国营养学会」。同源同远端 id 走 UPSERT，重复点不会越积越多
17. **「USDA 一直失败」不是解析 bug，是公共 Key 的配额没了**（E38）。查法不是读代码而是 `curl -sD -` 看响应头：`429` + `X-Ratelimit-Limit: 10` + `Retry-After: 72874`。修法有三层：DEMO_KEY 与自有 Key 的 429 分开写文案（前者「公共池被用光，填自己的 Key 立刻恢复」，后者「你的配额用完了，等一小时」）、读 `Retry-After` 做本地冷却（冷却期内连请求都不发）、设置页给「去申请 API Key」链接与逐源「测试」按钮
18. **位置数组的映射不能靠语义推断，只能靠标签核对**（E40）。第 31 列按「矿物质后该跟维生素 E」猜成维 E，实际是碘（μg）；维生素 E 在第 16 列（α-TE，mg）。定位办法：把详情页 HTML 的 `<td>` 按顺序抽出来，等于给列表的每一列贴标签。番杏一行（13/16/31 三格都有值）已进测试当锚点
19. **缓存键要带上「要几条」**（E39）。设置页「测试」只取 2 条，与首页搜索（6 条）同键，点一次测试就把正常搜索结果覆盖成 2 条，用户会以为源坏了
20. **会删用户数据的按钮一律两步确认**。应用里没有通用对话框，所以让按钮自己上膛：第一次点击只改文案（「再点一次清空」）并给 6 秒后悔期，第二次才执行。补录条目是用户自己攒的，删掉没法从离线库重查回来

### W8 导入导出（完成）
- T8.1 备份包格式：ZIP（`manifest.json` + `users` / `favorites` / `meals` / `settings`），带 `formatVersion` 与 `schemaVersion`

实现要点：

1. **包里不出现数据库主键**。档案用包内 `ref` 关联，导入时逐个重映射成新主键。否则把这台机器的备份导到另一台，收藏与记录会全部指向不存在的档案——这是最容易写错、也最难在单机上测出来的一处
2. **为每类数据定义独立 DTO**，不复用 EF 实体。实体上有年龄、BMI、关注项解析等计算属性，直接序列化会把内部结构焊进文件格式；DTO 也让「哪些字段进包」变成可审阅的一行行代码
3. **枚举存文本而非数字**（`"LoseWeight"`、`"Diabetes, Hypertension"`），解析失败退回默认值而不是整包失败。`Enum.IsDefined` 对 `[Flags]` 组合值一律返回 false，是这条路上一脚踩空的坑（见 E24）
4. **冲突语义分三种**：合并＝只补不覆盖、覆盖＝同名档案按备份重写并清空其收藏与记录、只补新档案＝同名整体跳过。判断同名用档案名
5. **判重不靠主键**：收藏按 `(档案, 食物 id)`，用餐记录按「同人同天同餐同名同量+创建时刻」的内容指纹
6. **CSV 带 BOM**：中文 Windows 的 Excel 会把无 BOM 的 UTF-8 当 GBK 打开，满屏乱码
7. **API Key 默认不导出**，需显式勾选，界面直接说明「包里是明文」
8. 导入全程单事务；结束后补一次「必须有一个当前档案」的兜底

- **测试**：新增 `DailyAdviceTests` 21 项（摄入拆解 3、进度判定 4、目标折算 1、每日建议 12、排序 1），全量 231 项
- **自检截图**：`page=advice` / `page=nav-collapsed` / `page=imported`，归档至 `docs/shots/`

实现要点：

1. **快照不够，要回成分表重算**。`MealEntry` 只存 6 项快照（能量、蛋白、脂肪、碳水、纤维、钠），而建议页要看 20 多项。所以 `IntakeBreakdown` 按 `FoodId` 去重后逐个回查成分表，乘重量累加；查不到详情的条目退回快照并计入 `SnapshotOnlyCount`，页面据此标注「部分条目只有 6 项」
2. **「没测过」和「没吃够」是两件事**。`NoData` 与 `Insufficient` 严格分开：整日无记录、或该营养素在所有条目里都没值时是 `NoData`（显示「无数据」且不参与「未达标」计数），只有真测到且低于 80% 才是 `Insufficient`。混在一起会让用户以为「今天钙严重不足」，其实是库里没这项
3. **达标阈值分两类**。推荐量（RNI/AI）80%–120% 算达标，超过 120% 只提示不警告；上限类（钠、糖、胆固醇、反式脂肪）70% 起「接近」、超过 100% 才「超出」——等到 95% 才提醒，剩下两餐已经来不及
4. **上限类单独分栏**。把钠和钙放在同一张表里，用户会误以为钠也该「吃够 2000 mg」。语义不同就不能同表
5. **脂肪与碳水必须按供能比折算，不能写死克数**。DRIs 给的是 AMDR 区间（脂肪 20–30%、碳水 50–65%），`DriTable.FatGrams` / `CarbGrams` 取中值（25% / 55%）按能量换算。第一版漏了这两项，建议页的「能量与宏量」卡片只剩蛋白质和纤维两行
6. **建议要能给「依据」，也要能给「今天多少」**。每条 `AdviceItem` 都带 `Basis`（指南名称）与内联的实际值。只说「少盐」是废话，说「今天钠 1490 / 1500 mg」才有用
7. **排序稳定且按严重程度**。同级建议保持规则定义顺序，避免每次刷新顺序跳动
8. **折叠状态存进同一个 `AppPreferences` 对象**。主题、字号、折叠各存各的键，但读写走同一次 `Load`/`Save`，避免两次写入互相覆盖

### 补充轮次：家用量词表（完成，2026-10-25，T8.5.3）

上一轮把「同一个东西」认清楚了，这一轮解决「吃进去多少」——用户不会为记账去称重，只会说「一碗」「一个」。

- 新模块 `Core/Nutrition/PortionUnits.cs`：每个食物给出 2 个快捷档位（「半碗 · 110 g」「一碗 · 220 g」）与一句倒推描述（「≈ 一碗」）
- 数值全部来自《中国居民膳食指南》科普版的表 3-1-1（标准量具）、表 3-1-2（参考手势）、表 3-1-3（每类食物的标准份）：碗 = 口径 11 cm 直口碗（一份米饭 110 g 为半碗，故满碗 220 g）、杯 = 250 ml、勺 = 10 ml 瓷勺（油 10 g）、一掌心肉 40~50 g、双手一捧蔬菜 100 g、单手一捧坚果 10 g。逐条对照见 `docs/09-膳食指南对照.md` §2.7
- **名称优先、分类兜底**：`米饭(蒸)(均值)` 按「米饭」走碗，`鸡蛋(土鸡)` 按「鸡蛋」走个，命不中再按 `group_key` 走「一捧 / 一掌心」
- 两个数字不能混用：`UnitGrams`（一个碗 220 g）决定「≈ 一碗半」怎么说，档位（半碗 110 g）只是快捷写入。混用会把 50 g 米饭说成「半碗」——因为它对 110 g 的档位取了 0.5 倍
- 倒推容差 −22% ~ +20%：一杯 250 ml 装 200 ml 牛奶（指南的一份）读作「一杯」，而不是「0.8 杯」；50 g 米饭离一碗太远，直接不给量词
- 落点两处：详情页「加入今日餐次」、记录页编辑浮层。记录里没有分类，编辑浮层只按名称推量词

**踩过的坑**：半碗 110 g 与「半」这个字重复折算，导致 50 g 米饭被标成半碗；改成一单位基准 + 档位两套数字后才对。以及 DevShot 按 `Bounds.Height` 挑 ScrollViewer 会挑到侧栏，滚动执行了画面却不动——改成「按钮所在的祖先 ScrollViewer」。

### 补充轮次：接口地址自动补 /v1（完成，2026-10-26，测试反馈）

用户配 `https://api.hncsec.cn/`（服务商文档只给域名），点「选择」查模型列表报「返回的不是合法 JSON」；
同一份地址与 Key 在 Cherry Studio 里能正常列出模型。

- 根因：程序在裸域名后直接拼 `/models`，请求打到站点首页（`200 text/html`）。接口实际挂在 `/v1` 下——
  实测 `/models` 返回首页 HTML、`/v1/models` 返回 19 个模型的 JSON（含用户手填的 `DeepSeek-V4.1-Flash`）。
  Cherry Studio 的差别只在于它默认补 `/v1`。
- 新增 `Core/Recognition/OpenAiEndpoint`：**路径为空补 `/v1`，路径不为空原样使用**。
  不猜「`/api` 该不该接 `/v1`」——猜错比不猜更难排查。`ChatCompletions` / `Models` / `ModelUrls` / `ChatUrls`
  四个入口共用同一套规则，界面预览与真实请求不会各算一套。
- 候选回落：`{归一化}/models` → `去掉版本段/models`。只在 404/405、或响应以 `<` 开头时换地址；
  401/403/429/5xx 不重试（Key 错了、服务端崩了，换路径只会白等一轮）。
- **200 也可能是 HTML**：网关对未知路径常直接返回站点首页，状态码仍是 200。判定因此不看状态码，
  改看响应正文开头；全部候选失败时，错误信息写明实际请求过的地址与响应截断。
- 设置页接口地址下方从写死的「程序会请求 {BaseUrl}/chat/completions」改为实时预览「将请求 …」，
  用户能立刻看出程序到底打到哪。

### 补充轮次：分享当天的餐次明细（图片与 Markdown）（完成，2026-10-26）

一天记完，用户会想把它发到家庭群、或者贴进自己的周报。这轮在「餐次明细」标题行右侧加了一个分享按钮，
两条路：**图片**与 **Markdown**。

**一、Markdown 走文本剪贴板**

- 排版在 `Core/Sharing/MealShareFormatter`，与「复制当天记录」共用同一份数据但排版不同：那份是自己扫一眼的
  （对齐、缩写），这份要能粘进文档继续排版，所以带标题（`# 2026-10-26 周一 饮食记录`）、
  按早/中/晚/加分组且每组带小计（`## 早餐 · 174 kcal`）、`## 全天合计` 与末尾
  「由 NutriTrack 生成 · 数据仅供参考，不替代医嘱」；
- 三处「空着也要好看」的细节都有测试钉住：没有记录时直说没有而不是给一张空表、空餐次不出现小标题、
  没有档案名时不留一个孤零零的点。

**二、图片走控件渲染，不走第二套排版**

- 分享范围在 XAML 里包成一个命名容器 `ShareArea`（标题 + 日期 + 图例 + 各餐次卡），导出的就是屏幕上看到的；
- 实测踩到三个坑，都写在 `Services/ShareSnapshot` 的注释里：
  1. `RenderTargetBitmap.Render(Visual)` 在这套 Avalonia（11.3）里对**非根控件**只画出实心矩形——餐次明细
     渲出来只剩图例里两个圆点。改成「整窗渲染 → 裁目标区域」；
  2. `DrawingContext.DrawImage` 的源矩形按**像素**取，不是布局单位。画布是 2 倍图，裁剪矩形不乘倍率，
     拿到的是放大后的左上角一块（第一版导出 3 KB，几乎全空）；
  3. 区域比视口高时按屏分片再拼接（`ShareSnapshot.Compose`），否则记录多的一天会把晚餐整段漏掉。
- 截图期间把窗口内所有按钮的 `Opacity` 设 0：收图的人点不了，留着只会让人以为发错了东西。
  **不能用 `IsVisible`**——「回到最上」的可见性有绑定，滚动时会把它重新写回 true，分享图右下角就多一个绿圆点；
  浮层（常用组合）不在 `ShareArea` 里，所以藏的是整窗按钮而不是区域内按钮；
- 四周留 14 单位底色边距：文字贴着边缘，转存到白底编辑器里很难看。

**三、图片进剪贴板只能落到宿主这一层**

- Avalonia 11 的 `IClipboard` 只有文本、文件与自定义格式，没有图片。`IDesktopShell.TryCopyImage` 在 Windows
  实现里走 WinForms 的 `Clipboard.SetImage`——它要求 STA，而 Avalonia 桌面端 UI 线程正是 `[STAThread]`；
- 没有这个能力的宿主（Android、截图自检用的 `NullDesktopShell`）**如实说「当前平台不支持」**，
  不给「已复制」的假回执。

**自检**：`NUTRITRACK_SHOT=out.png NUTRITRACK_SHOT_PAGE=tracker NUTRITRACK_SHOT_SHARE=clipboard` 会走与按钮
完全相同的路径（含分片与隐藏按钮）另存一张 `out-share.png`，再写一次剪贴板并打印结果；`..._SHARE=text`
直接打印 Markdown 全文。

**回归**：`dotnet build` 0 警告 0 错误；`dotnet test` 472 项全绿（新增分享排版 9）；截图 `tracker-share.png`
（记录页：餐次明细标题行右侧的分享入口）、`tracker-share-share.png`（1816×1008 的 2 倍图，四餐完整、
按钮已隐去、边距均匀）；剪贴板实测写入成功（103 KB）。

### 补充轮次：草酸分级、肾结石档案与中文名（完成，2026-10-27）

A6 上一轮只补了嘌呤，结石人群仍然只拿到通用建议。这轮把草酸补齐，顺手把项目的中文名定下来。

**一、草酸不走实测，走估算（与嘌呤同一套理由）**

- 成分库里没有 `oxalate` 列，公开成分表的草酸数据只覆盖几百种食物，硬凑一张表等于给 4.4 万条里绝大多数编数字；
- `Core/Nutrition/OxalateCatalog` 按「名称特征 → 类别基线 → Unknown」给三级：高 > 100、中 25–100、
  低 < 25 mg/100 g。判不出来给 `Unknown`，界面**不占位**，而不是猜一个「中」；
- **基线不能照抄嘌呤那张表**：肉、水产、蛋、奶在嘌呤里是中高，在草酸里是低——草酸几乎只集中在植物性食物的
  少数几类（深绿叶菜的个别品种、根茎、坚果、可可、茶）。这一点写进注释，否则下一个人照搬嘌呤的 `Switch`
  就会把整块肉都判成高草酸。

**二、误判比漏判更糟，两个坑都钉了测试**

- `"笋"` 单独一个词匹配不到「笋干」（中间隔了字），改成 `竹笋 / 春笋 / 冬笋 / 笋干` 逐个列；
- 反过来，「莴笋」含「笋」被误判成高草酸。`Traps` 表专门收这类名字带词、实际很低的特例
  （杏仁豆腐、杏仁露、茶油、油茶、抹茶蛋糕、可可蛋糕、莴笋）。
  漏判只是少一条提醒，误判会让用户把一道普通菜永久划进禁区。

**三、接到四条路上，不只是加个卡片**

| 位置 | 表现 |
| --- | --- |
| 详情页 | 草酸卡（等级胶囊 + 区间 + 估算口径），排在嘌呤卡之后；档案里有肾结石时提示「焯水去掉三到五成、与含钙食物同餐」 |
| `AdviceRules.OxalateRule` | 高草酸给 `Warning`（避免），中草酸给 `Caution`（限量）——把 50 mg 的东西按禁忌给，用户只会不再相信这个列表 |
| `FoodRanker` | 高草酸压 5 分并挂「草酸高」标签；低草酸**不加分**，结石真正吃亏的是菠菜那几样，压分就够 |
| 识别候选 | 肾结石用户拍到一盘菠菜，标「高草酸」——不告诉他比不推荐更糟 |

**四、膳食原则补三条（`DietGuidelinePlanner` 肾结石章节）**

- 限量高草酸食物；饮水 2.5~3 L（这是复发预防里证据最强的一条，比限草酸更管用）；
- **钙要吃够，且与草酸同餐**——这条与多数人的直觉相反，所以文案必须把机制写出来：草酸在肠道里遇到钙
  先结合成不溶物随粪便排出，「限钙」反而让更多草酸被吸收。测试直接断言「同餐」「含钙食物」这些字在，
  写不明白就等于白写。

**五、中文名定为「知食」**

英文 `NutriTrack` 不动。三处显示位同步：窗口标题 `知食 NutriTrack`、侧栏品牌（`知食` + 副标题
`NutriTrack · 食物成分与营养跟踪`）、托盘提示 `知食 NutriTrack · 食物成分与营养跟踪`（63 字符上限内）。
没选「营养师」「食医」这类词——程序给的是分级与原则，不做诊断。

**回归**：`dotnet build` 0 警告 0 错误；`dotnet test` 508 项全绿（新增草酸分级 29、规则与膳食原则 7）；
截图 `detail-oxalate-spinach.png`（菠菜：高草酸红卡 + 区间 > 100 mg）、
`detail-oxalate-spinach-advice.png`（同页建议区「警示 · 高草酸，肾结石需限量」）、
`advice-stone-expanded.png`（长期饮食原则里三条肾结石条目）、`detail-oxalate.png`（丝瓜：低草酸，卡片不误报）。

### 补充轮次：菜名写法归一与 Windows 安装包（完成，2026-10-27）

两件事一起做，因为它们是同一个问题的两端：**搜得到**（数据层）与**装得上**（分发层）。

**一、菜名写法归一（A1 收尾）**

- 成分表写「番茄」、菜谱作者写「西红柿」，`LIKE` 匹配对这种差异零容忍。做法是给每条菜名
  生成等价写法写进 `food_alias`，检索链路一行都不用改；
- `tools/fooddb/dish_names.py`：26 组同义写法，先替换一处再替换第二处（「西红柿炒鸡蛋」→
  「番茄炒蛋」要两步），每条最多 8 个，两字以内不写（「番茄」会命中上百道菜）；
- 两条纪律写进代码注释：**保护复合词**（「鸡蛋→蛋」遇到蛋糕/蛋挞/蛋黄就不替换，否则
  「鸡蛋糕」变成「蛋糕」）、**不覆盖正式名**（库里真有一条「西红柿炒蛋」时，别名不该把它改指到别人身上）；
- 结果：全库 6,963 条别名、覆盖 3,598 道菜。搜「西红柿鸡蛋三文治」命中「番茄蛋三文治」。

**二、发布打包工具**

工具分三层，职责不混：

| 项目 | 职责 |
| --- | --- |
| `NutriTrack.Packaging` | 目标矩阵、校验、发布计划、`dotnet publish` 调用、安装包拼装（无 UI 依赖，可单测） |
| `NutriTrack.Setup` | 安装器外壳：解压、写快捷方式、写注册表、卸载 |
| `NutriTrack.Publisher` | Avalonia 界面 + `--build` 命令行 |

几条关键决定：

- **Windows 7 / 8.1 明确标成不支持**（**下一轮已推翻**，见「打包工具支持 Win7 / 8.1」）。
  当时的理由是 .NET 8 运行时要求 Win10 1607 起步；但那是支持范围而不是启动条件，
  Win7 SP1 实机验证可跑，所以后来改成「能生成 + 把补丁前提讲清楚」；
- **安装包 = 外壳 exe + 追加负载 + 64 字节尾部记录**（偏移 / 长度 / SHA-256）。Windows 加载
  exe 只看 PE 节表，尾部字节会被忽略，外壳仍能启动。不用 Inno Setup / WiX / NSIS，因为那三样
  都要额外装一套工具链，而打包本来就要用 dotnet SDK；
- **装到 `%LOCALAPPDATA%\Programs`、不提权**（**下一轮已改**：默认改成非系统分区的
  `Program Files\<应用名>`，理由与做法见「打包工具补丁」那一轮）；
- **散装发布而不是单文件**（**下一轮已改**：单文件成为所有目标的默认，散装退为可选项。
  当时的顾虑是「单文件要解压到临时目录」，但那个代价只出现在
  `IncludeNativeLibrariesForSelfExtract` 打开时，本工具没有开）；
- **附带文件必须显式列出来**：成分库不在 `.csproj` 的发布范围里，开发机上会向上找到仓库里的库，
  装到干净机器上就只剩「未找到成分库」。`ReleaseRequest.Content` 就是为这件事加的，
  界面默认带上 `data/food_full.db` → `data/food_full.db`；
- **通用化**：`IPackageBuilder` 按平台查表，Android 只差一个实现（`AndroidPackageBuilder` 已占位并
  如实返回「W9 未完成」）；`ReleaseCatalog` 是「哪个组合能选」的唯一出口；命令行与界面共用同一套请求模型。

**验收**（x64，`docs/10-发布打包.md` 有完整记录）：发布 517 个文件 / 105.6 MB 负载 → 安装包 168.9 MB；
`/silent /dir` 装到测试目录，519 个文件、快捷方式与卸载项齐全；从安装目录启动后首页显示
「离线库 · 44,688 种食物」，证明库被正确找到；`/uninstall /quiet` 之后目录、注册表项、快捷方式全部清除。

**回归**：`dotnet build` 0 警告 0 错误；`dotnet test` 522 项全绿（新增打包 12、检索 2）；
`python tools/fooddb/test_dish_names.py` 11 条通过；截图 `publisher.png`（打包工具界面）、
`installed-home.png`（从安装目录启动）、`search-dish-alias.png`（同义写法检索命中）。

### 补充轮次：头像、侧边栏快捷切换与凭据加密（完成，2026-10-27）

三件互不相干但都指向「像一件成品」的小事：家庭成员该有自己的脸、换人记账不该绕路、
存在库里的 Key 不该是明文。

**一、用户头像（`AvatarPattern` / `AvatarView` / `AvatarImageStore`）**

- 三种来源：**默认头像**（8 套配色 + 统一剪影）、**随机图案**（5×5 左右对称的 identicon）、
  **上传照片**（居中裁成正方形、缩到 256 px 存 PNG）；
- 图案由 FNV-1a 从昵称算出：同一个名字在任何机器上都长一样，所以老档案升级**不需要回填**，
  库里也不用存图片；种子落进 `users.AvatarValue`（schema 11），点「换一个」才换脸；
- 编辑档案时把种子**固化**下来：不固化的话，改个昵称一家人的头像全变了；
- 照片一律入库前裁剪缩放，文件名用 GUID：手机原图 4 MB / 4000×3000 直接塞进列表会卡，
  而头像最终只显示 40 px 的圆；
- 备份包带 `AvatarKind` / `AvatarValue`，但**不带图片本体**——跨机器导入后照片找不到，
  界面自动退回图案头像（`AvatarImageStore.Resolve` 返回 null），整次导入不会因此失败。

**二、侧边栏：版本信息搬家 + 用户快捷切换**

- 右下角原来那两行（版本 + 免责声明）撤掉：**版本进标题栏**（`知食 NutriTrack 0.1.0`）与
  **设置页底部「软件信息」卡**（软件名称、版本、运行环境、用户库结构版本、凭据存储方式）。
  版本号只有一个来源 `Core/AppInfo`，读 `Directory.Build.props` 的 `Version`；
- 原来的位置改成**当前用户卡**：头像 + 昵称 + 性别年龄，点开弹出成员列表（点一下即切换）、
  「查看当前档案」「新建一位成员」；折叠到只剩图标时收成一个圆形头像，功能不变；
- 切换后顺手刷新当前页（`IPageActivation`）：首页建议、记录页配额都是按人算的，
  不刷新就会显示上一个人的数据；
- 折叠按钮换成**面板图标**（圆角方框 + 左侧实心竖条），展开态用同一份几何做 `scale(-1,1)` 镜像，
  不再维护两份坐标。

**三、API Key 加密落盘（E11）**

- `Core/Security/ISecretProtector`：`enc:v1:` 前缀 + Base64，`Protect` 对已加密值幂等，
  `Unprotect` 认不出的值返回空而不是抛异常——**一个 Key 读不出来不该让程序打不开**；
- Windows 用 **DPAPI**（当前用户作用域 + 固定熵）：密文绑账户，别人拷走 `user.db` 也解不开；
  其它平台（将来的 Android）退到**密钥文件 + AES-GCM**（`avatars` 同级的 `secrets.key`），
  挡得住「库被单独拷走」，挡不住能读应用私有目录的 root，这一点写在设置页里；
- 加密只发生在**仓储层**：`VisionProviderRepository` 与 `OnlineSourceConfigStore` 写入加密、
  读出解密，上层（设置页、识别器、搜索源）看到的永远是明文。保存后要把调用方手里那个对象
  改回明文，否则设置页会突然显示一串 Base64；
- 启动时 `SecretMigration` 把历史明文补一次（幂等，第二次是空转），只认 `vision_providers.ApiKey`
  与 `app_settings` 里 `online.*.api_key`；主题、字号这些不是凭据，加密它们只会让用户看不懂配置文件；
- **备份包仍是明文**：包要能导到另一台机器上还原，DPAPI 密文跨不了机器。默认不导出 Key，
  勾选时界面明确提示（`docs/04-备份与导出.md` §1.3）。

**回归**：`dotnet build` 0 警告 0 错误；`dotnet test` **542 项全绿**
（新增头像图案 7、凭据加密与迁移 10、仓储密文 2、schema v11 迁移 1）。
截图：`profile.png` / `profile-edit.png`（头像三选一与预设配色）、`settings.png`、
`settings-about.png`（软件信息卡）、`nav-collapsed.png`（新折叠图标与折叠态头像）。

### 补充轮次：打包工具支持 Win7 / 8.1（完成，2026-10-28）

上一轮把 Win7/8.1 标成「不能生成」，理由是 .NET 8 的运行时的最低版本是 Win10 1607。
用户在 Win7 SP1 实机上用自包含发布跑通了主界面，推翻了这个判断：**那是支持范围，
不是启动条件**——运行时里并没有一道「低于 6.2 就退出」的检查。

**一、目标矩阵**

- `windows7` / `windows81` 的 `IsSupported` 改为 true，`Note` 写明三条补丁：
  KB2670838（Direct2D/DirectWrite，Avalonia 要用）、KB2999226（UCRT）、
  KB2533623（.NET 加载原生库依赖的 API）。缺一项就是双击没反应；
- 新增 `CombinationError`：Win7/8.1 选 `arm64` 直接拦住——这两个系统没有 ARM64 版本，
  给个「提醒」等于允许用户生成一个永远装不上的包；
- 新增 `PrefersSingleFile`：Win7/8.1 默认单文件。只有这个形态在真机上验证过，
  已验证的形态就是默认形态；Win10 以上维持散装，缺 dll 时一眼能看出来。

**二、发布形态变成可选**

- `ReleaseRequest.SingleFile`（`bool?`，`null` 表示按目标系统取默认）；界面上是
  「打包成单文件」复选框，切换系统版本时重置回默认值；
- 命令行 `--single-file` / `--multi-file`，不写就按目标取；
- 单文件**只收拢托管程序集**：Skia、ANGLE 这些原生库仍在目录里（不设
  `IncludeNativeLibrariesForSelfExtract`），首次启动不会把几十 MB 解压到 `%TEMP%`。

**三、两处顺手的修正**

- **产物名带系统版本**：`{应用名}-{版本}-{osKey}-{架构}-setup.exe`。原来同一 RID 下
  Win7 的包与 Win10 的包同名，后生成的会把前一个覆盖，最后剩哪个说不清；
- **底栏加「打开输出目录」**：生成成功后点亮，用 `ShellExecute` 打开产物目录——
  中文路径不必自己加引号，也不用让用户照着日志里的长路径去翻。

**四、界面上的一处纠错**

Win7 能选之后，`NoteText` 原来只在 `IsSupported == false` 时才显示，导致补丁前提

### 补充轮次：打包工具的四个补丁（完成，2026-10-28）

用户提了四件事：单文件该是通用默认、安装位置该按分区剩余空间来定、要能选独立 / 框架依赖、
构建日志是乱码。

**一、单文件成为通用默认**

`ReleaseCatalog.PrefersSingleFile` 恒为 true。上一轮「Win7 用单文件、其余散装」的区分取消了：
单文件只收拢托管程序集（没开 `IncludeNativeLibrariesForSelfExtract`），Skia / ANGLE 仍在旁边，
不会出现「首次启动解压几十 MB 到 %TEMP%」的代价。散装保留为复选框，给排障用。
顺带去掉了「切换系统版本重置单文件」的行为——默认值对所有目标一样，重置只会踩掉用户的选择。

**二、安装位置**

新增 `NutriTrack.Packaging/InstallLocation.cs`：

- 盘：固定分区里排除系统盘，取剩余空间最大的那块；只有系统盘时退回
  `%LOCALAPPDATA%\Programs`（系统盘的 `Program Files` 要管理员权限，而安装器刻意不提权）；
- 目录：该盘的 `Program Files`（x86 包用 `Program Files (x86)`；盘上只建了另一个名字的目录时
  跟着已有的那个，不在同一块盘上摊出两套）；
- 再挂一层程序名，形如 `G:\Program Files\知食 NutriTrack`。

「自动补程序名」补在**用户点完浏览之后**，补完就在文本框里：看得见、改得动，删掉再点安装
就装到删剩的目录。补在安装那一刻的话，用户永远没办法表达「我就要装在这个目录本身」。
判断是否已有程序名用应用名的词（`知食` / `NutriTrack`），忽略大小写与空格；一个字的词不参与，
否则「食」会命中「食堂」。`/silent` 走同一套默认值，但 `/dir` 原样使用、不再补名——批量部署
需要可复现的路径。

顺带给 `Directory.CreateDirectory` 包了 `UnauthorizedAccessException`：用户硬选系统盘
`Program Files` 时给一句「需要管理员权限，请改建到其它分区」，而不是抛原始异常。

**三、部署模式**

`ReleaseRequest.SelfContained`（默认 true）。框架依赖时 `--self-contained false`，
产物名多一个 `-fdd`——同一组合下两种模式差一个数量级，光看名字分不出来就会发错包。

运行时探测分两次：

1. **生成前**（界面提示用）：读项目文件的 `TargetFramework` 与 `UseWPF` / `UseWindowsForms`。
   `net8.0-windows` 里没有点号的 `net48` 要排除掉，否则 .NET Framework 也会被当成 8。
   本机缺运行时只提示、不阻止：打包机常常不是目标机。
2. **发布后**（写 manifest 用）：读产物里的 `*.runtimeconfig.json`，这是权威答案——
   csproj 的属性可能来自 props 或 SDK 默认值。实测宿主项目虽然用 Avalonia，但因为托盘借了
   `NotifyIcon`（`UseWindowsForms=true`），正确答案是 `Microsoft.WindowsDesktop.App 8`。

安装器在目标机器上再查一次，缺运行时就在日志与状态栏写明「装完可能打不开」，同样只提示不安装
运行时——静默部署时发运行时是运维的事。

**四、日志乱码**

`dotnet publish` 重定向后输出 UTF-8，而 `ProcessStartInfo.StandardOutputEncoding` 不指定时
.NET 按系统 ANSI 代码页（简体中文 936）解码，于是「正在确定要还原的项目…」变成
「姝ｅ湪纭畾…」。`ProcessRunner` 显式指定 UTF-8 即可。

**回归**：`dotnet build` 0 警告 0 错误；`dotnet test` **572 项全绿**（新增 26 项，集中在

### 补充轮次：备份补上补录与自建菜品、Key 默认带上（完成，2026-10-28）

打包试点收尾后实测备份功能，用户指出三处与预期不符：导出的包不该缺补录条目与在线数据源配置，
API Key 的勾选也不该每次手动点。顺带清掉 `bak/` 里 150 MB 的临时库快照。

**一、格式升 v4：`foods.json`**

`local_foods`（在线补录 + 自建菜品）与 `custom_dish_items`（菜品配料）此前完全不在包里。
这两类都是用户自己攒的：补录来自在线搜索的「加入本地库」，自建菜品是一样一样搭的配料，丢了只能重来一遍。

- 身份是「来源 key + 来源内 id」，不是名字——名字会被来源改。自建菜品的 `RemoteId` 是创建时生成的 GUID。
- 条目带 `ref`（导出时的 `local_foods.Id`）。收藏 / 记录里指向本地条目的 `FoodId` 是它的**负数**，

- 配料的 `FoodId` 也可能是负数（配料本身是另一个自建菜品），所以统一等全部条目落库、映射建好之后再写。
- 校验阶段：v1~v3 的包没有 `foods.json`，其中的负数收藏找不到落点，直接剔除并记警告——
  留一条点开什么都没有的收藏，比干脆不要更让人困惑。

**二、API Key 默认勾选，且覆盖在线数据源**

`BackupExportOptions.IncludeVisionKeys` 改名 `IncludeApiKeys` 并默认 `true`。原先只有视觉模型受这个开关管辖，
`online.*.api_key` 不管勾没勾都**明文**写进包里、`includesSecrets` 却是 `false`——等于悄悄把 Key 送出去还贴着
「不含 Key」的标签。

现在两者同进同出：勾选时都还原成明文（跨机器还原必须如此，DPAPI 密文换账户解不开）；不勾选时
**一条 `*.api_key` 都不写**（写密文进去等于给用户一串解不开的乱码），视觉模型整段为空，
在线源的 `enabled` 开关保留（它不是凭据）。`includesSecrets` 改为按实际内容计算：勾了但库里没配 Key，
它仍是 `false`，导入前不会白紧张一次。

**三、`bak/` 清理**

`food_core.db.*` / `food_full.db.*` 的改造前快照、`user.db.*-pre-*`（含 `-shm`/`-wal`）、
四份截图用的临时 `user.db` 与一份乱码控制台日志，合计 151 MB，全部删除；按日期命名的源码快照 zip 与

**回归**：`dotnet build` 0 警告 0 错误；`dotnet test` **578 项全绿**（新增 6 项：默认含 Key、

### 补充轮次：提醒改成「一直挂着」（应用内浮层 + 常驻系统通知）（完成，2026-10-28）

打包试点之后连续测了几天，用户提出两件事：应用内的提醒是**顶上的一条横幅**，占着版面、看着像页面内容；
窗口不打开时虽然有系统通知，但**两秒就没了，通知中心里也找不到**。按他的原话，「提醒该等我自己关掉，而不是
自己消失」。

**一、应用内：横幅 → 浮层卡片**

- 从内容区的 `Grid.Row=0` 挪到覆盖整块内容区的 `Panel` 里，右上角、带描边与投影、`Surface` 底而不是浅绿底——
  它是「浮在页面之上的一层」，不能长得像这一页自己的卡片
- 不再占布局：页面标题、搜索框的位置不因提醒出现而跳动；切页、滚动都不跟着走，直到点「去记录」或 ×
- 窄屏（底部标签栏）改挂底部：顶部是页面标题，压上去等于把这一页的名字盖掉
- 不设自动消失的定时器——这是这次修改的核心诉求，不是遗漏

**二、系统通知：托盘气泡 → 真 Toast**

原来的 `NotifyIcon.ShowBalloonTip` 在 Win10/11 上只是一个旧式气泡：显示约两秒、不进通知中心、
`timeout` 参数被系统忽略。换成 `Windows.UI.Notifications` 的真 Toast：

- 未打包的桌面程序要先在 `HKCU\Software\Classes\AppUserModelId\NutriTrack.Desktop` 登记身份，
  否则 `CreateToastNotifier` 抛「找不到元素」。登记之后通知带程序名与图标，也进通知中心
- `scenario="reminder"` **单用不够**。实测（Windows 11 24H2）只有场景没有按钮时，25.9 秒仍会以
  `TimedOut` 收起——系统要有「一个可以等用户做的动作」才肯让卡片一直挂着。加一个
  `activationType="system" arguments="dismiss"` 的「知道了」后，45 秒仍在屏幕上，且点击确实关闭
- 按钮走**系统动作**而不是前台激活：未打包程序没注册 COM 激活器，`activationType="foreground"`
  的按钮点下去没有任何反应（实机验证过），等于给用户一个死按钮。系统动作由 Shell 处理，不依赖注册
- 窗口**最小化也算不可见**（`IsWindowVisible` 之前只看 `IsVisible`，最小化时仍为 true，提醒只挂在
  任务栏里的应用内卡片上，谁也看不到）
- 同一天同一种提醒只发一次（原来按 2 小时冷却，常驻之后重复弹只会叠卡片）；应用内点掉或做完之后
  调 `ClearNotification()` 把系统那条撤回，免得「记完体重回来，角落还写着今天还没称重」

**代价与边界**

- 加了 `net8.0-windows10.0.17763.0` 目标框架后，发布产物多一个 `Microsoft.Windows.SDK.NET.dll`
  （约 24 MB）。单文件包会一起变大，这是用系统 Toast 的固定成本
- Win7/8.1 没有 Toast 平台，`TryShowToast` 捕获异常后退回托盘气泡（它会自己消失，但总比不弹好）
- 点通知正文能把窗口带回来；点「知道了」只关闭，不弹窗口

**回归**：`dotnet build` 0 警告 0 错误；`dotnet test` **578 项全绿**（提醒逻辑在 UI 层，沿用既有测试；
本轮用临时宿主实测了通知生命周期的四条：发出、45 秒后仍在、`History` 计数为 1、`ClearNotification` 后归零）。
截图 `reminder.png`（桌面浮层）、`reminder-toast.png`（常驻系统通知）、`settings-reminder.png`（提示文案）更新。
截图期间不再启动提醒轮询——否则第 10 秒会自己浮出一张卡片，混进别的页面。

### 补充轮次：Windows 端补缺口（完成，2026-10-29）

先按「哪些地方会让用户卡住」盘了一遍 Windows 端还剩的缺口，交给他一份清单（P0 三项、提醒系统四项、
易用性五项）。他的处置意见是：开机自启要做（默认关）、「稍后 10 分钟」要做、库完整性检查要做、
**进程单例不做**（允许多开）、**多成员共用一份提醒不做**（提醒属于每个档案，单设备单用户但可多档案）、
自动更新等 Android 端基本完成后再统一做、P1-6 / P2-9 / P2-10 / P2-11 / P2-12 这几处该修、
Win10 以下的提醒按难度与必要性自行评估。这一轮按这个结论做完。

**一、开机自启动（默认关闭）**

- 写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值为 `"<exe>" --tray`。不用计划任务、
  不装服务——用户要的是「开机后它在那儿」，不是「多一个后台进程」
- **默认关闭**：往用户机器上写持久启动项属于越界，得他自己点头。开关失败（权限被组策略拦）时
  回滚按钮状态并在卡片上写明原因，不留一个「看着是开的、其实没写进去」的开关
- `IsEnabled` 不只看值存在，还要**校验指向的 exe 就是当前这个**：程序换目录（或从绿色版换成安装版）后，
  旧登记项指向一个已经不存在的路径，读值会说「已开启」，实际开机什么都不发生
- `--tray` 启动时窗口不弹出来，直接收进托盘。实现上不能只 `window.Hide()`——没 `Show` 过的窗口
  没有原生句柄，托盘图标会挂在一个不存在的窗口上，所以是「Show 之后在 `Opened` 里 Hide」
- 身份常量抽到 `src/Shared/AppIdentity.cs`（宿主与安装器各链接一份），只为一件事：**卸载时删的和
  安装时写的必须是同一个名字**，靠两处手写字符串迟早会打错

**二、提醒：稍后 10 分钟，记账改到档案上**

- 卡片上新增「10 分钟后」。按下之后 `EvaluateAsync` 在 10 分钟内直接返回，同时**把今天「已经提醒过」
  的记账撤掉**——不然 10 分钟后到点，判重会说「今天发过了」，按下去等于没按
- 原来「今天提醒过没有」存在全局提醒配置里（`MealPromptOn` / `WeightPromptOn`），家里两个成员
  切换时互相顶掉：甲早上称了体重，乙就收不到自己的那条。改成 `reminder.meal_prompt_on.u{id}` /
  `reminder.weight_prompt_on.u{id}` 两个键**按档案各记一条**，`ReminderSettings` 里只剩用户能改的项
  （开关、时间），`Clone()` / `SameAs()` 也跟着瘦下来
- 删档案时一并清掉它的记账键：`users.id` 会被 SQLite 复用，留着旧记账的话，新建的成员会和
  删掉的那个人共享「今天提醒过」，第一天就收不到提醒
- 这两组键是**运行时状态**，不是用户的设置：备份导出时按 `reminder.` + `_prompt_on` 剔掉。
  带进备份包再导回来，等于把「今天提醒过」从另一台机器搬过来

**三、库完整性自检**

设置页「本地数据」新增检查按钮，一次跑两组、九个检查项，全部**只读**（`Mode=ReadOnly` 连接，
不建表、不写迁移）：

- 成分库：文件在不在（含体积）、`PRAGMA quick_check`、`food` / `food_alias` / `dish_ingredient`
  三张表在不在、各行数是否为零
- 用户库：文件、`quick_check`、`PRAGMA user_version` 与 `AppDbInitializer.SchemaVersion` 是否一致、
  `users` / `meals` / `favorites` 的行数

三档状态：`Ok`（绿）/ `Warning`（琥珀，能跑但会缺东西，比如旧库没有别名表）/ `Failed`（红，页面上
直接说「请重新安装以还原成分库」）。按表名判缺失而不是只数行，是因为「表不在」和「表是空的」
对用户的含义完全不同：前者是装错了文件，后者是数据没导进去。**这一条是截图截出来的**——
第一版把表名写成 `foods`，界面上一本正经地报「这个文件不是本程序的成分库」，而它明明就是。

**四、备份：打开目录、拖进来、每周自动备一份**

- 三处路径行（成分库 / 用户库 / 应用目录）与日志目录都加了「在资源管理器中打开」；文件类型用
  `explorer /select,"…"` 定位到那一个文件，目录直接打开
- 备份包可以直接拖进设置页：走 Avalonia 11 的新拖放 API（`DragDrop.AllowDrop` 是附加属性，
  `e.DataTransfer.Contains(DataFormat.File)` 判断、`TryGetFiles()` 取文件）。拖入区做成虚线框 +
  上传图标——只有一行小字时没人会想到往上拖；拖到上方整块提亮，光标同时给「复制」符号
- **每周自动备份**：启动 20 秒后跑一次，距上次 ≥ 7 天才真正执行，保留最近 4 份，只删自己前缀
  （`NutriTrack自动备份-`）的 zip。自动备份**固定不含 API Key**：手动导出是用户自己决定要带 Key，
  自动的那份是后台悄悄写的，不该在磁盘上多留一处明文凭据
- 没做 `.zip` 文件关联，也没做双击打开。关联会把系统的压缩软件抢过来——双击任何 zip 都变成
  「导入备份」，这个误操作面比省一次点击大得多

**五、卸载残留与升级被占用**

- 安装前如果目标 exe 已存在，先把它关掉再解压。原来升级时旧进程占着文件，解压直接报「被占用」，
  用户看到的是一句英文异常和一个装了一半的目录
- 卸载时补删两处：`Run` 下的启动项（否则开机弹「找不到文件」）与
  `HKCU\Software\Classes\AppUserModelId\NutriTrack.Desktop`（不删的话通知中心里会留一条
  已经卸掉的程序）

**六、Win10 以下的提醒（评估后做了）**

Win7/8.1 没有 Toast 平台，原来退回 `NotifyIcon` 气泡——它两秒就没了，也不进通知中心，与「提醒要等
用户自己关掉」的结论相反。改成自绘浮窗（`NotificationWindow`）：无边框、`Topmost`、贴右下角、
带 × 与「打开看看」，等用户处理；只有 Info 类消息（测试通知）8 秒自动收。工作量约一个窗口的 XAML
加一处分支，难度低于「给 Win7 找一套第三方通知库」，所以做了。

**七、建议可以导出与打印（B7）**

「复诊时把这两周的饮食与缺口交给医生」原来只能靠截屏或口述。现在建议页标题栏多了「导出」与
「复制」，一次把整页内容整理成一份报告：

- 报告内容：档案与目标（含确诊、过敏原、重点关注、基础代谢）、今日摄入与目标、营养素完成度、
  今天的建议清单（带出处）、今天怎么吃、长期饮食原则、推荐食谱，末尾两段免责与数据来源
- **导出 HTML，而不是 PDF**：桌面端和 Android 都没有现成的 PDF 生成链，而 HTML 是「浏览器打开 →
  打印 / 另存为 PDF」的一条现成路——零依赖、零体积，样式写死在文件里，不联网也排版正常
- 版式按打印做：A4 边距、节标题不与内容分页、表格行不跨页；屏幕上看就是一页白纸，导出之前
  就知道打出来长什么样
- **数字必须和屏幕上一致**：报告只取界面上已经算好的文字，不重新查库。拿着两份对不上的资料去问诊，
  比没有资料更糟
- 用户文本一律转义（`AdviceReportFormatter.Escape`）：名字里带一个 `<` 就能让整页排版塌掉，
  而这份文件是要发出去的
- 营养素里没有数据的项不占一行（否则二十来行「今天没有测到」会把有结论的几项淹掉），
  汇成一句「以下 N 项成分库没有覆盖，本次不做判断：…」——省略的是行数，不是信息
- 「复制」给 Markdown，粘到聊天窗口就能发给家人；导出成功后标题下面出一行回执，写明文件名与
  「浏览器打开即可打印」。回执单独占一行，是因为文件名长，塞进标题栏会把按钮挤走

**八、明确不做**

- **进程单例**：允许多开。用户可能一边在记录页、一边想看详情，强制互斥只会让人骂
- **多成员共用一份提醒**：提醒属于档案，不属于机器
- **自动更新**：等 Android 端基本完成，做一套多平台一致的方案，而不是先给 Windows 造一个

W0–W2 落地过程中作了几处调整，均已在代码与文档中同步：

| # | 计划 | 实际 | 原因 |
|---|---|---|---|
| E1 | 全量库收录 16 个数据集 | 收录 6 个（USDA 3 + 日本主表 + 中国 + 台湾） | 日本「氨基酸/脂肪酸/碳水」附表与主表 **1996/1999 条同名**，多出的只是本项目不展示的细分项，收进来只会污染检索 |
| E2 | 移动端含日本主表 | 移动端只收中国 + 台湾，共 3,659 条 | 日本食物名是假名（`アマランサス　玄穀`），对中文用户零检索价值 |
| E3 | 用 FTS5 做模糊搜索 | 改用 `LIKE` + 预置拼音列 | unicode61 分词器会把整串中文当一个 token，2 字查询命中率为 0；44k 行 `LIKE` 全扫约 10–30 ms，足够快且行为可预测 |
| E4 | 未规划别名表 | 新增 `food_alias`（自动去括号 + 171 个通用名词） | 原库只有「红富士苹果」这类品种条目，没有「苹果」，搜通用名会得到一堆品种却无代表条目 |
| E5 | 引入 FluentAvaloniaUI | 未引入，改用自建设计令牌 + 控件模板 | 少一个依赖、Android 裁剪面更小、视觉完全可控 |
| E6 | 计划未含长度限制 | 剔除 11,659 条「零营养数据」食物 | USDA Foundation Foods 有 1.1 万条只有名称没有数值，展示出来是空壳 |
| E7 | — | 新增 `DevShot` 截图钩子 | 无人目视条件下核对布局；环境变量 `NUTRITRACK_SHOT` 触发，正式运行不生效 |
| E8 | .NET 9 | 全线下调到 **.NET 8（LTS）** | 用户要求长期支持版本。Core/Infrastructure/UI/Desktop/Tests 全部 `net8.0`；EF Core、`Microsoft.Data.Sqlite`、`Microsoft.Extensions.DependencyInjection` 同步降到 8.0.x |
| E9 | UI 库多目标含 android | 暂时只留 `net8.0`，Android 项目暂时移出解决方案 | 本机 android workload（35.0.105）只注册在 .NET 9 下，`net8.0-android` 报 `NETSDK1147`。W9 前需在 .NET 8 SDK 环境执行 `dotnet workload install android`，再把 Android 项目加回 sln |
| E10 | 用户库靠 `EnsureCreated` 建表 | 改为按 `PRAGMA user_version` 递增的幂等 DDL（`AppDbInitializer.Migrations`） | `EnsureCreated` 只在库不存在时生效，给已有 `user.db` 补 `vision_providers` 表**完全无效**，用户升级后一开设置页就崩。现为 `SchemaVersion = 2`，逐版本累加执行 |
| E11 | Key 存 Keystore / DPAPI | **已修（2026-10-27）**：Windows 用 DPAPI（当前账户 + 固定熵），其它平台用 `secrets.key` + AES-GCM；仓储层加解密，`SecretMigration` 启动时补历史明文 | 当时的判断是「与 W9 的平台服务一起做」，后来发现桌面端根本没有「等 W9」的理由：DPAPI 是现成的，且备份包不导出 Key 这条规矩已经存在。威胁模型的边界要说清楚——能登录同一 Windows 账户的人仍解得开，防的是「库被拷走」与「备份包被顺手打开」 |
| E12 | 计划未区分识别模式 | 拆成「拍菜品」与「拍营养标签」两条提示词，同一次调用只走其中一条 | 两者的输出结构不同（一个要克数，一个要每 100 g 数值），混在一条提示词里模型会互相干扰 |
| E13 | 识别结果只做展示 | 未匹配上时提供「在成分库里搜一下」，带名字跳搜索页且**不清返回栈** | 成分库是食材库，不是菜谱库，「宫保鸡丁」这类复合菜大概率匹配不到，得让用户自己去搜，同时又不能让他白拍一张 |
| E14 | 设置归属「我的」页 | 提升为左侧独立菜单项 + 全局 `app_settings`（主题/字号） | 设置是设备级的，与家庭成员档案无关；窝在档案页里意味着每换一个用户就要重配一次视觉模型。顺带在设置页展示数据路径，回应「库在哪」 |
| E15 | 缺口推荐按营养素绝对值排序 | 能量分支改走 `StapleKeywords` 主食词表 + 能量区间 + 密度排序 | 真实推荐结果是魔芋精粉（74 g 纤维、37 kcal）和麸皮：指标全场最高，但没人拿它补能量。营养指标排名靠前 ≠ 是能当饭吃的食物 |
| E16 | `pypinyin` 只是「可选增强」 | 改为构建时显式警告 + 报告拼音覆盖率 | 缺依赖时 `try/except` 静默降级，产出的库拼音列全空，`pg` 搜苹果失效但没人发现。重建时真实复现：旧库 6,164 条有拼音，新库 0 条 |
| E17 | 补充数据的分类直接走 `resolve_group` | 加 `_GROUP_REFINE`，只修正归到 `other` 的条目 | 野菜（婆罗门参、酸模、刺楸）、葡萄、薯条、香草全落到「其他」。修正后 other 从 45 降到 17，剩下的都是蜂产品与药食，与第 6 版归类一致 |
| E18 | 简单（4/9/4）Atwater 公式对含酒精食物偏得离谱 | 公式只用于**并列展示与偏差提示**，绝不回写 `energy_kcal` | 一度想让 `_sanity_check` 在偏差 >30% 时用公式覆盖能量，实测结果是啤酒 43→16（酒精 7 kcal/g 公式没这项）、稻麸 316→440、燕麦麸 246→397——用一条对高纤/含酒精必然失效的公式去「修正」实测值，比原数据更离谱。改为只报告 |
| E19 | GI 主名后备表只收「带括号条目去括号后的主名」 | 连本来就没括号的条目一起收，且「没括号的那条」优先 | 只收带括号的条目时，`苹果(均值)` 去括号得到 `苹果`，而 GI 表里的 `苹果` 自己没括号所以不在表里——最常见的水果反而查不到 GI。补齐后命中 265 → 377 |
| E20 | 关注指标到上限时替换最早选中的一项 | 直接拒绝，并提示「取消一项才能再选」 | 悄悄顶掉一个已有项，用户会以为自己点的那下生效了，直到发现另一个不见了 |
| E21 | 备份包直接序列化 EF 实体、沿用主键 | 为每类数据定义独立 DTO，档案用包内 `ref` 关联，导入时重映射主键 | 实体里全是计算属性（年龄/BMI/关注项解析），直接序列化等于把内部结构焊进文件格式；沿用主键则把备份导到另一台设备后，收藏与记录会全部指向不存在的档案 |
| E22 | 备份默认包含视觉模型配置 | ~~默认不含 API Key，需显式勾选~~ **已改（2026-10-28）**：默认包含（视觉模型 + 在线源同一个开关），取消勾选则一条 Key 都不写；界面明说「包里是明文」 | 备份包是普通 zip，随手发出去就等于送 Key。要能一键恢复旧设备，又不能让人无意中泄密，只能把选择权交出来并写清楚后果。当初选「默认不含」，是假设备份主要用于「同机还原」；实测下来第一用途是换机器/重装——默认不带 Key 等于每次还原都要重配一遍，用户还得自己去翻 Key |
| E23 | 导入只做「合并」一种 | 合并 / 覆盖 / 只补新档案三种，并逐条说明差别 | 「恢复旧设备」要的是覆盖，「把家人的备份并进来」要的是合并，两种语义差得远；只给一种，另一类用户会被静默改掉数据 |
| E24 | 枚举回读时统一用 `Enum.IsDefined` 校验 | `[Flags]` 枚举跳过这一步 | 第一版往返测试直接失败：`Diabetes \| Hypertension` 序列化成 `"Diabetes, Hypertension"`，`TryParse` 成功但 `IsDefined` 对这种组合值返回 false，回读后慢病全军覆没成 `None` |
| E25 | 缓存页返回时假定数据是最新的 | 加 `IPageActivation`，`GoBack` 时通知目标页刷新；只让需要刷新的页面实现 | 详情页「加入今天餐饮」直接写库，返回记录页看到的却是离开时的明细。做成基类虚方法会让每个页面都白重载一次，还会把用户翻到的位置重建掉 |
| E26 | 在线结果跨源去重按「名称」一刀切 | 有条例码用条码，否则「品牌 + 归一化名称」；不做跨语言合并 | 「纯牛奶」在伊利和蒙牛是两个商品，合并后数值谁都对不上；「Apple」与「苹果」是否同一条得靠人判断，机器硬猜会张冠李戴（雪梨 / pear / 梨） |
| E27 | 来源异常一律转成「失败」状态 | 先判 `OperationCanceledException` + 外层令牌已取消 → 原样抛出 | 单元测试直接抓到：用户划走页面被当成「请求失败」，界面上会闪出一排红色状态，其实什么都没坏 |
| E28 | 按计划把中国营养学会 / 香港 CFS 也做成「一源」 | 两个都不接：`nlc.chinanutri.cn/fq/` 实测是服务端渲染的分类目录页（`foodlist_*.htm`），无公开 JSON 接口；且其数据与离线库同源（食物成分表第 6 版）。CFS 是多步表单 POST | 为凑「三源」去写一个随时会挂的 HTML 爬虫，维护成本远高于收益；而且对中文用户来说「离线库已有」比「在线再查一遍同样数据」更有用。**前半段判断不完整，见 E37**：列表查询确有 JSON 接口，只是入口藏在表单 POST 里 |
| E29 | USDA 按营养素名称匹配 | 按 `nutrientId` 匹配（1008/1003/1004…） | 名称改过措辞：`Energy` 与 `Energy (Atwater General Factors)` 是两种写法，按名字匹配会静默丢能量 |
| E30 | 两个源的 `_100g` 数值单位相同 | USDA 的钠按 `unitName` 判断（mg 或 g），OFF 的矿物质一律 ×1000 | OFF 的钠 `0.0428` 表示 42.8 mg；不换算会显示成「钠 0 mg」，而「0 mg」和「没测」在用户眼里是两件完全不同的事 |
| E31 | 中文关键字也发给 USDA | 含 CJK 时直接返回空，不发请求 | 实测「苹果」在 USDA 返回 0 条，却白等 1.5 s 并消耗一次 DEMO_KEY 配额（30 次/小时）。中文查询整体耗时从 ~2.5 s 降到 ~1.1 s |
| E32 | `dataType` 里带上 `Survey (FNDDS)` | 只留 `Foundation,SR Legacy` | USDA 网关对 dataType 里的括号一律 400（编码成 %28 也一样），写成 `Survey` 又匹配 0 条。FNDDS 是美国人群调查的混合菜品，本来也不该用来查食材 |
| E33 | 直接采信 USDA 的相关度排序 | 请求放宽到 `take × 4`，本地按「关键字位置 → 名称长度」重排后截断 | 实测按 `apple` 搜，前三条是 Croissants / Strudel / Babyfood juice——用户查苹果却拿到苹果馅饼 |
| E34 | 缓存的时间列用 `DateTimeOffset` | 落库改用 `DateTime`（UTC），对外仍是 `DateTimeOffset` | 第一版缓存测试全红：`ExecuteDeleteAsync` 里 `FetchedAt < cutoff` 直接抛「LINQ expression could not be translated」——SQLite 提供程序不支持 `DateTimeOffset` 的比较运算。这类异常还被「缓存失败不致命」的 catch 吞掉，表现为「缓存写了但读不到」，比报错更难查 |
| E35 | 流式接口也直接产出按优先级排好的序列 | `StreamAsync` 产出完成顺序，`SearchAsync` 按 `Order` 重排后再合并 | 两个来源同时返回时，完成顺序不确定。旧测试「来源按配置的优先级排序」因此变得不确定；更实际的影响是同一关键字两次搜索的条目顺序可能互换，用户会以为数据变了 |
| E36 | 结果头写「找到 203 条」但列表只有 60 条 | 拆成「离线库 60 条（共匹配 203）」，在线另计一条 | 一层 60 条是界面上限。只写总匹配数会让人一直往下滚去找那 143 条，找不到就以为程序漏数据 |
| E37 | （修正 E28）中国营养学会「没有 JSON 接口」 | 有：`POST FoodInfoQueryAction!queryFoodInfoList.do`，form 表单，返回 `list` 为**位置数组**的 JSON；详情页才是 HTML | 用户实测给出接口后复验：苹果 229 kJ、钙 4 / 磷 12 / 钾 119 / 钠 1.6 与成分表第 6 版逐位吻合，位置映射可靠（见 `docs/05-在线数据源.md` §11）。E28 的「接不了」改为「当轮没找到接口」，T7.5 按列表接口先做，详情页解析留后 |
| E38 | 「USDA 一直失败」当作解析 bug 查 | 先 `curl -sD -` 把响应头打出来：`429 Too Many Requests` + `X-Ratelimit-Limit: 10` + `Retry-After: 72874`，确认是**公共 DEMO_KEY 的配额被全世界用光**，再动代码 | 单看「没有结果」这一个现象，可以怀疑解析、编码、超时、URL 任何一处。响应头一次就把范围收到「配额」上。顺带纠正文档里的老说法：DEMO_KEY 实测只有 10 次/小时，不是 30。修法也变了——不再是「稍后再试」，而是 DEMO_KEY 与自有 Key 分开写文案 + 本地冷却（冷却期内不发请求） |
| E39 | 设置页的「测试」按钮直接复用搜索缓存 | 缓存键追加 `\|n{条数}` | 测试只取 2 条，与首页搜索（6 条）同键。点一次测试就把 6 条的结果覆盖成 2 条，用户回首页发现「苹果」莫名少了一半，还以为源挂了。这类「另一个入口顺手写坏了主入口的数据」在缓存层最隐蔽：没有异常、没有日志，只是数字变小了 |
| E40 | 按「矿物质后面该跟维生素 E」把 list 第 31 列映射成维 E | 31 是**碘 μg**；维生素 E 在第 16 列（标签 α-TE，单位 mg） | 苹果、黄豆这两条的第 31 格都是空的，肉眼看不出错。拿番杏一对就露了：`0.9μg` 不可能是维 E（mg）。回详情页逐行对齐才定死顺序——**位置映射不能靠语义推断，只能靠标签核对** |
| E41 | 在线条目只做展示，不能「加入一餐」 | 加「加入本地库」（补录）：落 `user.db` 的 `local_foods`，id 取负数，记住来源 | 所有下游功能（记录、收藏、日汇总）都要一个 `FoodId`，在线条目只有「来源 + 远端 id」。两条路：给下游都加「可能没有 FoodId」的分支（改动面大、容易漏），或把在线条目变成有 id 的本地记录（改动集中在一个存储层）。选后者；负数 id 让「离线权威数据」与「本机补录」在同一个 id 空间里也能一眼分开，且补录永远不会写进只读库 |
| E42 | 建议分散在详情页卡片与记录页缺口提示里 | 独立成「建议」页（侧栏第 4 项），四组进度 + 分级别建议清单 | 详情页只能回答「这个食物该吃多少」，记录页只能回答「今天还差多少」，没有一个地方回答「我今天整体吃得怎么样」。而 20 多项营养素塞进记录页会把最常用的记账动作挤下去 |
| E43 | 营养素进度只分「达标 / 未达标」 | 四态 + `NoData` 独立：未达标（<80%）、达标（80–120%）、偏高（>120%）、无数据 | 「没测过」和「没吃够」混在一起时，整日无记录会被报成「13 项全部未达标」，用户会以为身体出了大问题，实际是库里没这些值。`NoData` 必须既不计入未达标、也不显示 0% |
| E44 | 补录条目只有「清空」 | 新增补录管理页：列表、按名称/来源筛选、行级删除、查看详情 | 清空是不可撤销的整体操作，用户攒了十几条补录却只能全删。列表 + 单条删除才让「补录」从临时手段变成可维护的数据 |
| E45 | 文案与实现口径不一致三处 | 逐一修正：补录页「冰箱」（功能不存在）、「添加糖」实为总糖（库无 `added_sugar`）、建议页免责措辞与另两页不统一 | 承诺不存在的功能比缺功能更伤——用户会去找那个入口；用总糖对比添加糖上限会误报（500 ml 牛奶 + 一个苹果总糖 35 g，添加糖接近 0），文案必须直说这是上界估算。详见 `docs/06-功能盘点与路线图.md` §七 |
| E46 | GI 只吃成分表那一份 259 条的附表 | 四源合并（成分表 / glycemic-index.net / health.db / 国际表）+ 人工校准，377 → 916 条，新增 `glycemic_load` 与 `gi_source` | 单源覆盖太窄，糖尿病用户的「低 GI」提示只在小部分食物上生效。合并的关键不是源多，而是**优先级**：同源同命名的排最前，出处不明的只补位。GL 一律用库内碳水重算——直接采信源里的 GL 会出现「碳水 20 g、GL 15」这种读不通的组合 |
| E47 | 用户给的两份网页 GI 表也一起入库 | 两份都不采用，理由写进 `docs/07-血糖数据说明.md` §3 | alsearsmd 的表 GI 出现 110、蔬菜肉类一律记 0（把「不含碳水」当「GI=0」）、葡萄糖与面包基准混用；weightlossresources 质量没问题但全是英国超市品牌，中文库匹配率近零。**用户给的数据也要看能不能用**——错的 GI 比没有 GI 更误导 |
| E48 | `apply_gi` 按「carb 在 21 位」取碳水 | 实际 carb 在 20 位、21 位是 fiber。修正后挂载数从 152 恢复到 770（再调阈值到 916） | 症状极具欺骗性：不报错，只是轻轻少了 80% 的命中。为什么会漏？因为判断条件 `carb >= 5` 拿纤维值去比，只有高纤维食物才通过。**元组下标这种隐式契约必须写成常量并标出完整列位** |
| E49 | 重建库后拼音列全空，测试「拼音首字母搜苹果」失败 | `pypinyin` 未安装，构建脚本静默降级（E16 同一坑的复现）；装上后重建，拼音 7,225 条恢复 | 这类降级必须让构建**失败**而不是警告：拼音为空时程序照常能跑，只有拼音搜索这一条路静默失效，不写测试根本发现不了 |
| E50 | 三餐建议里「取不到该营养素」当成 0 | 改为取不到就跳过该条规则 | 快照只有 6 项，手工录入的条目没有钙钾，`?? 0` 会报出「钙还差 1000 mg、已摄入 0 mg」——用户会以为自己一天没摄入任何钙。和进度条里 `NoData` 与 `Insufficient` 分开是同一个判断 |
| E51 | 「模型列表返回的不是合法 JSON」当成解析问题查 | 拿同一份 Key 直接请求两个地址：`/models` → `200 text/html`（站点首页），`/v1/models` → `200 application/json`（19 个模型）。根因是裸域名少了版本段 | 报错落在解析层，坏掉的是路由层。对照 Cherry Studio 一秒定位：它显示 `https://api.hncsec.cn/v1/responses`，说明它默认补 `/v1`。修法不止补 `/v1`：还要在**状态码 200 时识别 HTML**（网关把首页兜底返回给未知路径），并在失败信息里打出实际请求过的地址——否则下次换个服务商，用户仍然只看到同一句「不是合法 JSON」 |
