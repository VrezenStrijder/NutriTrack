# 发布打包说明

> 版本：v1.2 · 2026-10-28
> 相关：`docs/01-开发计划.md`（里程碑）、`docs/06-功能盘点与路线图.md`（C5 缺口）

## 一、这个工具解决什么

开发机上 `dotnet run` 能跑，不等于用户装得上。打包工具做三件事：

1. 按目标系统版本与位数做一次**自包含发布**（目标机器不需要装 .NET 运行时）；
2. 把发布产物、附带的数据文件打成一个安装包；
3. 用户双击安装包 → 装到自己的用户目录 → 有快捷方式、有卸载项。

界面在 `src/NutriTrack.Publisher`，逻辑在 `src/NutriTrack.Packaging`，安装器外壳在 `src/NutriTrack.Setup`。三层分开是为了：逻辑能被单测覆盖、Android 将来只换一个打包器实现、外壳可以被任何 .NET 桌面程序复用。

## 二、能选什么

| 目标 | 可选 | 说明 |
| --- | --- | --- |
| Windows 10（1607 及以上） | ✅ | 官方支持范围内的最低版本 |
| Windows 11 | ✅ | 含 ARM64 |
| Windows 8.1（含 Update 1） | ✅ 需补丁 | 不在 .NET 8 的官方支持范围，实测可启动；见下节 |
| Windows 7 SP1 | ✅ 需补丁 | 同上 |
| Android 6.0（API 23）及以上 | ✅ | 最低版本取项目文件里的 `SupportedOSPlatformVersion`；Release 包必须有 `signing.props` |

架构：Windows `x64` / `x86` / `arm64`，Android `arm64` / `x64` / `arm`。**Win7 与 8.1 没有 ARM64 版本**，选了会被校验直接拦住，不是给个提醒了事。

发布形态有两个维度，互相独立：**单文件 / 散装目录**（`--single-file` / `--multi-file`）与**独立 / 框架依赖**（默认独立，`--framework-dependent` 切换）。这两个概念只对 .NET 桌面发布成立，Android 上由 SDK 自己决定。

### Android：APK、AAB 与 ABI

| 产物 | 能不能装 | 什么时候要 |
| --- | --- | --- |
| **APK**（默认） | 能 | 自测、发给用户 sideload、自动更新下载的就是它 |
| **AAB** | 不能 | 只用于上传应用商店，商店会按设备拆出对应的 APK |
| APK + AAB | — | 会连续编译两次，耗时翻倍 |

ABI 是两套互不兼容的原生库打包方式：

| ABI | 适用 | 说明 |
| --- | --- | --- |
| `arm64`（arm64-v8a） | 2017 年后的真机 | 唯一需要对外分发的形态 |
| `x64`（x86_64） | 模拟器、极少数 x86 平板 | 装到真机上会直接 `INSTALL_FAILED_NO_MATCHING_ABIS`；**不对外发布**，只在本地调试时单独出一条 |
| `arm`（armeabi-v7a） | 老设备 | 单独放到列表里，不进「全部 ABI」：32 位设备已经很少，多一个 ABI 就多一次完整编译 |

发布器把「系统 + 架构 + 产物类型」做成一张**可多选**的清单，界面里勾、命令行里用 `--target`：

| Id | 显示 | 默认勾选 |
| --- | --- | --- |
| `windows10-x64-setup` | Windows 10 / 11 · 64 位 | ✅ |
| `windows10-x86-setup` | Windows 10 / 11 · 32 位 | |
| `windows10-arm64-setup` | Windows 10 / 11 · ARM64 | |
| `windows7-x64-setup` | Windows 7 / 8.1 · 64 位 | ✅ |
| `windows7-x86-setup` | Windows 7 / 8.1 · 32 位 | |
| `android-arm64-apk` | Android · arm64（真机） | ✅ |
| `android-arm64-aab` | Android · arm64（AAB，仅上架） | |
| `android-x64-apk` | Android · x64（模拟器） | |

`NutriTrack.Publisher --targets` 打印这张表。每个勾选都要跑一遍完整的 `dotnet publish`，八个全勾就是八次编译——默认只勾三种真机形态，别的一律按需。

`versionCode = 主×10000 + 次×100 + 修订`（0.3.0 → 300），由 `Directory.Build.props` 的 `Version` 派生。打包日志里会打出这个数字。

### Windows 7 / 8.1：能跑，但不受官方支持

微软只声明 .NET 8 支持 Windows 10 1607 及以上，可运行时里并没有一道「低于 6.2 就退出」的检查。在打齐补丁的 Win7 SP1 上，本项目的自包含发布**实测可以正常运行**——用户在 Windows 7 旗舰版 SP1 上跑通了首页、食物详情与 GI/GL 卡片。

代价是这些机器必须先具备三样，缺了就是「双击没反应」：

| 缺什么 | 补什么 |
| --- | --- |
| 平台更新（Direct2D / DirectWrite） | KB2670838，Avalonia 渲染要用 |
| 通用 C 运行库（UCRT） | KB2999226 或 KB3118401 |
| 原生库加载 API | KB2533623 或 KB3063858，.NET 加载 `e_sqlite3.dll` 这类文件的前提 |

三条都写进了打包工具选项区的提示，也会在构建日志里留一行。**生成器不会替用户装补丁**——安装器只负责把文件放对位置。

> 之前这里写着「不支持 Win7」，理由是「运行时下限」。那个判断错了：下限是**支持范围**，不是**启动条件**。改成「能生成 + 把前提讲清楚」更诚实。

## 三、产物与目录

一次生成会在输出目录里留下这些东西：

```
artifacts/installers/
├── publish/win-x64/                                ← dotnet publish 产物（可直接绿色运行）
├── payload/win-x64/payload.zip                     ← 安装包的负载：manifest.json + app/**
├── stub/win-x64/NutriTrack.Setup.exe               ← 编译好的安装器外壳（可复用）
├── NutriTrack-0.3.0-windows10-x64-setup.exe        ← 独立（自包含）
└── NutriTrack-0.3.0-windows10-x64-fdd-setup.exe    ← 框架依赖（只在选了这个模式时出现）

artifacts/android-release/
├── NutriTrack-0.3.0-android-arm64.apk              ← 真机分发用（2017 年以后的设备）
└── NutriTrack-0.3.0-android-x64.apk                ← 模拟器 / x86 平板
```

**文件名只保留英文**。显示名（开始菜单、卸载列表）可以是「知食 NutriTrack」，落盘的名字会自动从中抽出 ASCII 部分：

| 显示名 | 产物文件名 |
| --- | --- |
| `知食 NutriTrack` | `NutriTrack-0.3.0-windows10-x64-setup.exe` |
| `知食 Nutrition`（英文词在中间） | `Nutrition-0.3.0-windows10-x64-setup.exe` |
| `知食`（整段中文） | 退到项目文件名：`NutriTrack.Desktop-0.3.0-…` |

规则是「ASCII 字母、数字、`_`、`-`、`.` 保留，其余字符当分隔符并折叠成一个下划线」。这样做的原因不是洁癖：GitHub 上传时会把 asset 名里的非 ASCII 前缀直接截掉（`知食_NutriTrack-…` 变成 `_NutriTrack-…`），而 `update.json` 里的下载地址是按文件名拼的，客户端于是拿到一个 404——这类问题只有真点一次更新才会暴露。空格顺带也解决了：它在命令行要引号、在 URL 要 `%20`、在 shell 脚本里不加引号就断成两个参数。

**文件名里带系统版本**：不同系统版本的包内容不同，不带版本号的话后生成的会覆盖前一个。**框架依赖再多一个 `-fdd`**：同一个组合下两种模式的体积差一个数量级，发错包的概率比想象中高，名字里必须能分辨。**Android 带 ABI**：arm64 与 x64 是两份互不兼容的安装包，装错了系统会直接回 `INSTALL_FAILED_NO_MATCHING_ABIS`。

安装包 = **外壳 exe + 追加的负载 zip + 64 字节尾部记录**。Windows 加载 exe 时只看 PE 头声明的节，尾部多出来的字节会被忽略，所以外壳仍能正常启动。尾部记录写明负载的偏移、长度与 SHA-256，安装前校验，避免下载不完整装出半个程序。

不用 Inno Setup / WiX / NSIS 的原因：那三样都要额外装一套工具链，而这里只需要 dotnet SDK——打包本来就要用它。代价是安装逻辑要自己写，也就是 `NutriTrack.Setup`。

### 单文件还是散装

**默认单文件，所有目标一致**。分发给别人的只有一个 exe，用户不用在几十个 dll 里找主程序，也不会出现「复制时漏了某个文件」这类问题。

| 形态 | 何时用 | 代价 |
| --- | --- | --- |
| 单文件（默认） | 正常分发 | 主程序变成一个 190 MB 级的 exe，杀毒软件的首次扫描会慢一些 |
| 散装目录 | 需要在安装目录里逐个文件排障 | 几十个文件，缺了哪个肉眼不一定看得出来 |

界面上是「打包成单文件」复选框，命令行是 `--single-file` / `--multi-file`。单文件**只收拢托管程序集**：Skia、ANGLE 这些原生库仍在目录里（没有设 `IncludeNativeLibrariesForSelfExtract`），所以首次启动不会把几十 MB 解压到临时目录。

### 独立还是框架依赖

| 模式 | 产物 | 目标机器要求 |
| --- | --- | --- |
| **独立**（默认，自包含） | 自带 .NET 运行时；程序本体约 171 MB | 无 |
| **框架依赖** | 不含运行时；程序本体 171 MB → 18 MB，整包 165 MB → 102 MB | 必须先装 **.NET 8 桌面运行时**（`Microsoft.WindowsDesktop.App`） |

选框架依赖时，工具会读项目文件（`TargetFramework` + `UseWPF` / `UseWindowsForms`）判断需要哪个运行时，并**在本机探测一次**：

- 本机没装 → 黄条提示「如果安装包就在这台机器上用，请改选独立；只是在这里打包、拿到别的机器装则不受影响」；
- **不阻止生成**。打包机往往不是目标机，用本机的状态去否决用户的决定是错的。

Win7 / 8.1 上选框架依赖会额外提示一句：**.NET 8 的运行时装不进 Win10 以前的系统**（官方安装程序本身就要求 1607+），所以这两个系统实际上只有「独立」一种可用选择。这条同样只提示、不拦——用户可能只是想生成一份包拿到别处用。

发布完成后还会读产物里的 `*.runtimeconfig.json` 拿权威答案（csproj 的属性可能来自 props 或 SDK 默认值），把运行时名与主版本写进 `manifest.json`。安装器在目标机器上再查一次，缺运行时就在界面上写明「装完可能打不开」——同样只提示，不拒绝安装。

> 为什么这里没有省得更多：安装器外壳必须是自包含的（目标机器可能连 .NET 都没有，装不起来就什么都做不了），它自己就占 64 MB；再加上 96 MB 的成分库压缩后仍有 25 MB。真正的节省在程序本体（171 MB → 18 MB），包体只从 165 MB 降到 102 MB。

## 四、装到哪里

默认位置按这个顺序定：

1. **非系统分区里剩余空间最大的那块盘**（只有系统盘时退回当前用户的 `%LOCALAPPDATA%\Programs`——系统盘的 `Program Files` 要管理员权限，而安装器刻意不提权）；
2. 该盘的 `Program Files`（32 位包用 `Program Files (x86)`；如果盘上只建了另一个名字的目录，就跟着已有的那个，不要在同一块盘上摊出两套）；
3. 再挂一层**程序名**：`D:\Program Files\知食 NutriTrack`。

程序名是在**用户点「浏览」选完目录之后**补的，补完就摆在文本框里：

```
选 D:\Program Files       → 文本框变成 D:\Program Files\知食 NutriTrack
选 D:\Apps\NutriTrack     → 文本框中已经有程序名，不再追加
把名字手工删掉再点「安装」 → 就装到 D:\Program Files 本身
```

补在「选完」而不是「安装时」，是为了让用户看得见、改得动。默认补名如果发生在安装那一刻，用户就永远没办法表达「我就要装在这个目录本身」。判断是否已含程序名用应用名的词（`知食`、`NutriTrack`），忽略大小写与空格。

静默安装（`/silent`）也走同一套默认值；但 `/dir` 是**原样使用**，不再补名——批量部署时脚本写的是完整路径，安装器擅自加一层会让「装到哪」随安装器版本变化，没法复现。

## 五、安装器做了什么

- 装到系统盘以外的 `Program Files`（规则见上节），**不提权**：目录由当前用户创建，所以不需要管理员；只有用户手动选了系统盘的 `Program Files` 才会被拒，那时给一句明确的提示而不是原始异常；
- 框架依赖包在安装前会查一次本机运行时，缺了就在日志与状态栏写明「装完可能打不开」，但不阻止安装；
- 开始菜单快捷方式必建，桌面快捷方式按用户勾选；
- 注册表 `HKCU\...\Uninstall\<应用名>` 写入显示名、版本、安装位置、图标、卸载命令与占用大小，「应用和功能」里能看到、能卸；
- 安装目录里放一份只含外壳头部的 `uninstall.exe`（不带 100 MB 负载），卸载走它；
- **升级时先关掉正在运行的旧进程**：目标 exe 已存在就先 `CloseRunning`，再解压。原来的顺序是先解压，
  旧进程占着 `NutriTrack.exe` 与几个 dll，解压直接抛「文件被占用」，用户看到的是一句英文异常和一个
  装了一半的目录（2026-10-29 修）；
- 卸载：删快捷方式 → 删注册表 → 结束正在运行的实例 → 删文件 → 删不掉的交给 `cmd /c rmdir` 延后清理；
- **卸载还要清掉程序在系统里留下的两处痕迹**（`AppUserModelId` 与开机自启）：
  - `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` 下的 `NutriTrack` 值——不清的话，用户开机时
    会被系统弹一句「找不到文件」，而他并不知道那是卸载残留；
  - `HKCU\Software\Classes\AppUserModelId\NutriTrack.Desktop` 整棵子键——不清的话，通知中心里会留一条
    已经卸掉的程序，点它什么也不会发生；
- 这三组名字（AUMID、启动项值名、`--tray` 参数、两个注册表路径）放在 `src/Shared/AppIdentity.cs`，
  宿主与安装器各链接一份：**安装时写的和卸载时删的必须是同一个字符串**，靠两处手写迟早会打错；
- 校验失败、路径非法（含 `..`）、负载里没有主程序，都会中止并给出原因，不留半装状态。

## 六、怎么用

### 图形界面

运行 `NutriTrack.Publisher`，按四步填完左栏：

1. **版本与名称**：版本号默认取 `Directory.Build.props`；应用名可以是「知食 NutriTrack」，文件名会自动取其中的英文部分。
2. **项目与输出**：Windows 宿主项目与 Android 宿主项目分开填（一次发布通常两个都要）。
3. **发布目标**：勾选要出的包，**可以多选**。默认勾了三种真机形态（Windows 10/11 64 位、Windows 7/8.1 64 位、Android arm64 APK），其余（32 位、ARM64、AAB、模拟器包）按需勾。
4. **清单与 GitHub**：默认生成 `update.json`；勾上「上传到 GitHub」后填仓库、tag 与更新说明，就会在同一次操作里把产物传上去。

底栏三个入口：

| 按钮 | 做什么 |
| --- | --- |
| **生成** | 按勾选顺序逐个打包 → 写清单 →（若勾了）上传，进度条显示当前文件与百分比 |
| **生成一键脚本** | 把当前勾选固化成 `release-<版本>.ps1`，双击即可重跑同一套发布 |
| **打开输出目录** | 生成过一次后可用，直接跳到产物所在位置 |

左侧「随包附带」默认已经带上 `data/generated/food_full.db` → `data/food_full.db`。**这一项不能漏**：程序按 `AppContext.BaseDirectory\data\` 找成分库，开发机上它会向上找到仓库里的库，装到干净机器上就只剩「未找到成分库」。

「打包成单文件」默认勾上，对所有 Windows 目标一致，取消勾选就输出散装目录。「部署模式」默认「独立（自包含）」；切到「框架依赖」时会提示目标机器需要预装运行时，但**照样让你生成**。

### 命令行（CI 用）

一次发布多目标、写清单、上传，全都在这条里：

```bash
dotnet run --project src/NutriTrack.Publisher -- --publish \
  --version 0.3.0 --out artifacts/release \
  --target windows10-x64-setup --target windows7-x64-setup --target android-arm64-apk \
  --name "知食 NutriTrack" \
  --notes "修正配料两列布局" \
  --upload
```

- `--target` 可重复，也接受逗号分隔；不带时用默认三种（`--targets` 列出全部 Id）。
- `--manifest` 指定清单落点（默认 `<输出目录>/update.json`），`--no-manifest` 跳过。
- `--upload` 才会联网；token 优先读 `GITHUB_TOKEN`，否则用 `gh auth token`。tag 已存在时复用，同名资产先删后传。
- `--script <路径>` 生成一键脚本；只给 `--script`（不给 `--publish`）时仅写脚本、不打包。

旧的单目标 `--build` 仍然可用（`--os` / `--arch` / `--family` 那一套），适合只想出一个包的时候。

包已经打好、只想补一份清单：

```bash
NutriTrack.Publisher --manifest-only --out artifacts/release --version 0.3.0 --notes "…"
```

`tools/make-update-json.ps1` 现在就是这个命令的包装，参数形状没变。

### 静默安装（部署与验收用）

```bash
"NutriTrack-0.1.0-windows10-x64-setup.exe" /silent /dir D:\Apps\知食 NutriTrack
"<安装目录>\uninstall.exe" /uninstall /quiet
```

`/silent` 不建桌面快捷方式、不启动程序——自动化里启动一个常驻托盘的进程会挡住后续清理。不带 `/dir` 时按默认规则选位置（见 §四）；带了 `/dir` 就原样使用，不再补程序名。

## 七、验收记录

> 下面三组是 **2026-10-28 打包试点** 的实测数据。当天晚些时候桌面项目换成了
> `net8.0-windows10.0.17763.0`（为了发常驻的系统 Toast，见 `docs/01` 的补充轮次），
> 发布产物会多一个 `Microsoft.Windows.SDK.NET.dll`（约 24 MB，单文件包里也在其中）。
> 新包体积在原数字上加 20 MB 左右，安装/卸载流程本身没有变化；没有重新出全套验收数据。

### Windows 10 x64 · 独立（自包含）单文件（2026-10-28）

| 项 | 结果 |
| --- | --- |
| 发布 | 12 个文件（`NutriTrack.exe` 171 MB + 10 个原生库 / `icon.ico` + `data/`）、负载 101.5 MB |
| 安装包 | 164.8 MB，SHA-256 `a8949de3…`（每次重编外壳都会变） |
| 默认安装位置 | `G:\Program Files\知食 NutriTrack` —— 本机非系统分区里 G 盘剩余最多（639 GB） |
| 静默安装 | 退出码 0，`/silent` 不带 `/dir`，注册表 `DisplayVersion 0.1.0`、`EstimatedSize 356254 KB` |

## 八、已知边界

- **没有代码签名**。首次运行会被 SmartScreen 警告；企业分发前需要买证书并对 setup.exe 签名。注意追加负载会让签名失效——要签就必须签在追加之后。
- **没有增量包**。升级 = 再装一次新版本（会覆盖文件、更新注册表版本号）。安装前会自动关掉正在运行的旧实例，用户不必先手动退出。完整包约 100 MB，流量敏感的场景还没有差分方案。
- **自动更新不校验签名，只校验 SHA-256**。清单由自家发布，哈希能防传输损坏与挂在半路的半包，但防不住仓库被完全接管；真要抗这一层需要 Authenticode（Windows）与签名证书比对（安装包本身已由 keystore 签名）。
- **Win7 / 8.1 只在一台 x64 机器上验证过**：x86 版本能生成，但没有在 32 位老机器上装过；Win8.1 完全没实机验过（补丁清单与 Win7 相同，风险应该一致，但这是推断不是实测）。
- **x86 与 ARM64 未实机验证**：发布参数与架构映射有单测，但没有在 32 位系统或 ARM 设备上装过。真要用之前先找一台机器验一遍。
- **安装包不携带系统补丁**。Win7/8.1 缺 UCRT 就是双击没反应，安装器不会替你装 KB2999226——静默安装场景下发补丁是运维的事。
- **框架依赖包不会替你装运行时**。缺 `Microsoft.WindowsDesktop.App 8` 就是双击没反应，安装器只在界面上提示，不会去下载 .NET（那需要另一套引导程序与签名）。
- **框架依赖包不能跨大版本**：锁的是主版本 8，目标机器装的是 .NET 9/10 不行，必须装 8.x；这是 .NET 的默认行为，不是本工具的取舍。
- **Android 的 AAB 不写进更新清单**：AAB 不能直接安装，写进去客户端也用不上；要上商店的那份单独传。

## 九、自动更新与清单发布

客户端从 GitHub 拉一份 `update.json`，比对版本后按「平台 + 架构」挑包下载。Windows 静默覆盖当前安装目录，Android 下载完交给系统安装器。**没有任何一步会静默替换程序**：最后一下必须用户点。

### 9.1 清单格式

仓库根目录的 `update.json`（当前主分支）：客户端先读它，读不到再试 `releases/latest/download/update.json`。

```json
{
  "LatestVersion": "0.3.0",
  "ReleaseDate": "2026-11-04",
  "UpdateLog": "修正配料两列布局；食谱支持一键加入记录",
  "ReleasePage": "https://github.com/VrezenStrijder/NutriTrack/releases/latest",
  "Assets": [
    {
      "Platform": "windows10",
      "Architecture": "x64",
      "Url": "https://github.com/VrezenStrijder/NutriTrack/releases/download/v0.3.0/xxx-setup.exe",
      "Sha256": "…64 位小写十六进制…",
      "Size": 107374182
    },
    { "Platform": "android", "Architecture": "arm64", "Url": "…apk", "Sha256": "…", "Size": 46000000 }
  ]
}
```

老格式（`LatestVersion` + `Version_Win7` / `Version_Win10` 平铺链接）仍然认，`Assets` 优先。以后加字段不要改名，改名等于让所有老客户端失联。

`Platform` 只认三个值：`windows10`（含 Windows 11）、`windows7`（含 8.1）、`android`。客户端用 `Environment.OSVersion` 判断，Win11 报的是 10.0，所以**清单里不要写 `windows11`**——生成脚本会自动并入。

### 9.2 清单怎么来

清单由打包工具自己写，不再由脚本扫目录反推：

```powershell
NutriTrack.Publisher --publish --version 0.3.0 --out artifacts/release --target windows10-x64-setup --target android-arm64-apk
```

流水线手里有每个产物的真实来源（哪个目标、哪个架构、versionCode 多少），比从文件名猜准。规则：

- **AAB 不进清单**：它不能安装，写进去只会让客户端下载到一个装不上的文件。
- **`windows11` 并入 `windows10`、`windows81` 并入 `windows7`**：客户端按 `Environment.OSVersion` 判断，Win11 报的是 10.0，清单里写 `windows11` 的话 Win11 用户永远匹配不到。
- **同一平台同一架构只留一条**，重复的会列在日志的「未写入」里。

只想给已经打好的包补一份清单：

```powershell
NutriTrack.Publisher --manifest-only --out artifacts/release --version 0.3.0
```

`tools/make-update-json.ps1` 是它的包装，参数形状不变（`-Version` / `-ArtifactsDir` / `-Output` / `-Notes`），内部转调发布器——**清单逻辑只有一份**，不会出现脚本与工具不一致。

**清单不能手写。** 少写一条 Android 记录的表现是「手机上永远不提示更新」，而且不报错。

### 9.3 发布步骤

一条命令做完（勾了「上传」时连 Release 与 main 分支一起更新）：

```powershell
NutriTrack.Publisher --publish `
  --version 0.3.0 --out artifacts/release `
  --target windows10-x64-setup --target windows7-x64-setup --target android-arm64-apk `
  --notes "本次更新内容" --upload
```

它依次做：

1. 按目标逐个 `dotnet publish`，产出 setup.exe / APK；
2. 汇总产物，算 SHA-256 与体积；
3. 写 `update.json`；
4. 上传到 GitHub：Release 不存在就建（tag 用 `--tag`，默认 `v{版本}`），同名资产先删后传，最后把 `update.json` 提交回 `main`。

上传时会打印每个文件的百分比（界面里是进度条）。150 MB 的安装包在慢网络下要看得出「在动」。

不勾上传就只在本机产出文件，自己拖到 Release 页面。**别忘了把 `update.json` 也传上去并提交回 main**——客户端主路径读的是 main 上的那一份。

发完之后用旧版客户端点一次「检查更新」，确认能检出、能下载、能装上。

**`--name` 可以写中文**，它会进快捷方式与卸载列表；文件名会自动取其中的英文部分，不需要为了文件名另起一个英文名。整段中文时退到项目文件名（`NutriTrack.Desktop` 会去掉宿主后缀变成 `NutriTrack`），仍然不会有非 ASCII 字符——中文 asset 名在 GitHub 上传时会被截断，清单里的链接就指向了一个不存在的文件。

### 9.4 一键脚本

界面上的「生成一键脚本」会写出 `release-<版本>.ps1`，内容就是上面那条 `--publish` 命令，参数与勾选完全一致：

```powershell
# 生成时间：2026-11-04 16:20   目标：Windows 10 / 11 · 64 位、Android · arm64（真机）
$publisher = 'D:\...\NutriTrack.Publisher.exe'
$arguments = @(
    '--publish'
    '--version'
    '0.3.0'
    ...
)
$process = Start-Process -FilePath $publisher -ArgumentList $quoted -NoNewWindow -Wait -PassThru
```

两个细节值得留意：

- **用 `Start-Process -Wait` 而不是 `&`**：发布器是 GUI 子系统（WinExe），直接调用时 PowerShell 不等待，`$LASTEXITCODE` 也是空的，脚本会在打包还没开始时就打印「完成」。
- **文件带 UTF-8 BOM**：Windows PowerShell 5.1 读无 BOM 的 UTF-8 会按系统代码页解析，中文应用名与更新说明会变乱码。

脚本与工具的差别只是「谁来点按钮」，执行路径是同一条 `ReleasePipeline`，所以不存在「工具能出、脚本出不来」的组合。

### 9.5 客户端行为

| 环节 | Windows | Android |
| --- | --- | --- |
| 检测 | 启动后延迟 4 秒静默检查（可在设置里关） | 同左 |
| 发现新版 | 屏幕右下角浮卡 + 设置页「软件更新」卡片 | 主界面内浮卡 + 设置页「软件更新」卡片 |
| 下载 | 下到 `<数据目录>/updates`，边下边算 SHA-256 | 同左，额外受 FileProvider 白名单约束 |
| 安装 | `setup.exe /silent /dir "<当前 exe 目录>" /restart` | 交给系统安装器（首次需授权「安装未知应用」） |
| 安装目录 | 取 `Environment.ProcessPath` 所在目录，**不问用户** | 不涉及 |
| 免安装运行 | 识别不到 `install.json`，按钮变成「打开发布页」 | — |

`/dir` 是必须的：安装器的静默模式在没传 `/dir` 时会按磁盘剩余空间重新挑目录，结果就是升级完变成两份安装。

### 9.6 失败时的表现

| 情况 | 用户看到 |
| --- | --- |
| 没网 / 域名解析失败 | 静默检查不打扰；手动检查显示「检查更新失败：…」并给出原因 |
| 清单 404 或格式坏了 | 同上，回退到第二个清单地址 |
| 这个平台这次没发包 | 「v0.3.0 已发布，但这个平台这次没有对应的安装包」 |
| 哈希不符 | 「安装包校验失败（SHA-256 不匹配），已丢弃」，文件被删掉 |
| 安装目录不可写 | 「安装目录没有写入权限…请到发布页手动下载」 |
| Android 未授权安装未知应用 | 跳到该应用的授权页，返回后需再点一次更新 |
