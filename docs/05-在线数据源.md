# 在线数据源

离线成分库（`food_full.db`）覆盖的是食材，不是菜谱，也不是商品。用户在超市拿起一包饼干
想知道热量时，离线库帮不上忙——那部分要靠在线源。另外离线库本身有覆盖面与更新节奏的
限制，在线源也是它的补丁。

本文讲**契约、聚合规则、缓存策略、界面接线与已接入来源的实现细节**。

## 1. 分层

```
     界面（首页搜索）
        │  离线库先出结果（~200 ms）        在线这一路异步补齐（1–3 s，逐源上屏）
        ▼                                    ▼
  IFoodQueryRepository            IOnlineFoodAggregator
  （只读成分库，本地）              OnlineSearchAggregator      并发 / 超时 / 去重 / 容错
        │  ▲                              │        ▲
        │  └─── ILocalFoodStore ──────────┘        └── IOnlineSearchCache（user.db，TTL 7 天）
        │       （user.db 在线补录，负 id）          │ 每个来源一条状态
        │                                  ┌───────┴─────────┬───────────────────┐
        ▼                                  ▼                 ▼                   ▼
   food_full.db                  ChinanutriFoodSource   UsdaFoodSource   OpenFoodFactsSource
   （只读，从不写入）             nlc.chinanutri.cn      api.nal.usda.gov  search.openfoodfacts.org
                                       Order = 10          Order = 20        Order = 30
```

**为什么把容错收在聚合器、而不是每个来源各写一遍**：每接一个新源都要在最慢那一步
（网络）上重复写超时、重试、异常映射，各源的行为必然不一致；出问题时界面只能看到
「没有结果」，到底是慢、是挂、还是没配 Key，谁也说不清。

来源的职责就一句话：**关键字 → 一批条目**，别的都不管。

## 2. 契约

### `IOnlineFoodSource`

| 成员 | 说明 |
|---|---|
| `Key` | 稳定标识（`chinanutri` / `usda` / `off`），缓存与用户开关都用它，不跟显示名一起改 |
| `DisplayName` | 界面上的来源名 |
| `ShortName` | 筛选条与状态条上的短名（`USDA`），默认等于 `DisplayName` |
| `Order` | 展示优先级，小的在前：中文源 10 → 国际源 20 → 商品库 30 |
| `RequiresCredential` | 是否要用户自备 Key。为 true 时未配置就不发请求 |
| `SetupUrl` / `SetupHint` | 要 Key 时「去哪儿申请、为什么需要」。没 Key 的源留空，设置页据此决定是否显示「去申请」链接 |
| `ProbeKeyword` | 设置页「测试」按钮用的探针词，默认「苹果」；英文源覆盖成 `apple` |
| `IsConfiguredAsync` | 现在能不能发请求。**不得联网探测**——它每次搜索前都会被调用，联网探测的成本和搜索本身一样大 |
| `SearchAsync` | 按关键字检索。没命中返回空列表，网络与解析错误直接抛 |
| `GetAsync` | 按来源内部 id 取详情。取不到返回 `null`，不抛异常——「这条被删了」和「服务挂了」是两回事 |

### `IOnlineFoodAggregator`

| 成员 | 说明 |
|---|---|
| `Sources` | 已注册来源，按 `Order` 升序（顺序在这里定死一次，否则同一组结果两次刷新的排序可能不同） |
| `SearchAsync` | 并发查询全部来源并合并；单源失败不影响整次搜索 |
| `StreamAsync` | **逐源产出**，谁先回来谁先出（`IAsyncEnumerable<OnlineSourceResult>`） |
| `SearchSourceAsync` | **只查一个源**，`sourceKey` 不认识时返回 `null`。界面上的「单源刷新」走这条，与 `StreamAsync` 共用同一套超时 / 缓存 / 状态归纳逻辑，不另写一份 |

`StreamAsync` 是界面默认走的路径：三个源各 2 s，等齐再显示就是 2 s 空白；流式的话
第一个源 1 s 出来用户就能开始看。它产出的顺序是**完成顺序**，而 `SearchAsync` 会把
结果按 `Order` 重排——一次性结果不能因为网络快慢而换顺序（E35）。

### `IOnlineSearchCache`

| 成员 | 说明 |
|---|---|
| `TryGetAsync` | 取缓存。过期 / 不存在 / 解析失败都返回 null，不抛 |
| `SaveAsync` | 写缓存。同源同关键字只留最新一条（UPSERT），顺手清 30 天前的行 |
| `ClearAsync` | 清空，设置页「清空缓存」用 |

配置由 `IOnlineSourceConfigStore` 存取：`online.{key}.api_key` / `online.{key}.enabled`，
环境变量 `NUTRITRACK_ONLINE_KEY_{KEY}` 优先于数据库（开发与自动化验证时不该为了跑一次就写进用户的库）。

## 3. 六种来源状态

`OnlineSourceResult.State` 每个来源必有一条，失败也有——界面只有拿到这个才能解释
「为什么只出来两个源」。

| 状态 | 含义 | 界面表现 |
|---|---|---|
| `Ok` | 成功且有结果 | 正常色，筛选条显示「USDA 3」 |
| `Empty` | 成功但没命中 | 「USDA 无结果」（这是有效信息，不是错误） |
| `Timeout` | 超过 8 s 未返回 | 「USDA 超时」。**慢 ≠ 坏** |
| `Failed` | DNS、连接被拒、非 2xx、解析失败 | 「USDA 失败」，筛选项弱化（`Opacity 0.55`） |
| `NotConfigured` | 缺 Key / 未启用，压根没发请求 | 「未配置」，引导去设置页 |
| `Disabled` | 用户关掉了 | 不显示 |

聚合结果上另有三个派生标记：`AllSourcesFailed`（全部不可用 → 应退回离线库）、
`HasPartialFailure`（有结果但某一路失败 → 标一句「部分来源超时」）、`DuplicateCount`（去重掉的条数）。

`NotConfigured` 与 `Failed` 还带一个 `Hint`（`OnlineSourceResult.Hint`）：一句话说清**下一步该做什么**——
「未配置 · 去设置页填 Key 后可用」比单写「未配置」有用得多，USDA 撞 429 时的那句
「公共 Key 配额用完了，填自己的 Key 或稍后再试」也是同一个字段。

## 4. 超时：用取消实现

`CancellationTokenSource.CreateLinkedTokenSource(ct)` + `CancelAfter(8 s)`。

- 默认 8 s：最慢的 USDA 跨洋、偶尔还要跳一次重定向，正常 1–2 s 回；超过 8 s 基本是网络有问题，继续等只会让整页卡住
- **区分「我们取消的」和「用户取消的」全靠外层令牌是否被触发**：外层被触发 → 原样抛 `OperationCanceledException`（用户离开页面，结果本来就不需要了）；只有内层超时 → 记 `Timeout`
- 顺序很关键：`catch (OperationCanceledException) when (ct.IsCancellationRequested) → throw` 必须写在超时分支之前，否则用户划走页面会被 `catch (Exception)` 收成「请求失败」，界面闪一排红色状态，其实什么都没坏（E27）

## 5. 结果缓存（T7.3）

落 `user.db` 的 `online_cache` 表（schema 5 新增，`AppDbInitializer` 里是幂等 DDL）：
一行一个「来源 × 关键字」，整组条目序列化成 JSON 存 `Payload`。

缓存的理由不是省流量，是三件具体的事：

1. 同一个词反复搜（返回上一页、切日期再切回来）不必再等 2 s；
2. 断网时还能看到上次查到的条目，而不是一片空白；
3. **USDA 的 DEMO_KEY 只有 30 次/小时**，缓存是最直接的配额保护。

规则：

| 规则 | 原因 |
|---|---|
| TTL 7 天（`OnlineSearchOptions.CacheTtl`） | 营养成分不会天天变，但也不能一直用旧值 |
| 键 = `kw:` + `TextNormalizer.Normalize(keyword)` + `|n{条数}`，有条码时 `bc:` + 条码 + `|n{条数}` | 「Apple」「apple!」共用一个键；条码直查与关键字检索不能互相顶替 |
| **条数也进键** | 设置页「测试」只取 2 条，若与首页搜索（6 条）同键，一次测试就会把 6 条的结果覆盖成 2 条，用户回到首页看到莫名其妙少了一半（E39） |
| **空结果不缓存** | 一条 7 天前的「无结果」会挡住用户重试，源恢复了也看不到 |
| **来源被关闭 / 未配置时先判配置再看缓存** | 用户关掉的源不该从缓存里继续冒出来 |
| 刷新按钮传 `SkipCache = true` | 刷新的语义就是「我不信缓存」 |
| 写缓存失败一律忽略 | 缓存是加速手段，不能因为写不进去就让搜索失败 |
| `FetchedAt` 用 `DateTime`（UTC）而不是 `DateTimeOffset` | SQLite 提供程序不支持 `DateTimeOffset` 的比较运算，「清理 30 天前的行」那句会直接翻译失败（E34） |

命中缓存时 `OnlineSourceResult.FromCache = true`、`CachedAt` 有值，界面显示
「3 条·缓存」并把状态行写成「在线 · 1/2 个来源 · 2 条（来自缓存）」。

## 6. 去重规则

同一个食物往往几个源里都有，全铺出来等于让用户自己判断「哪条是真的」。规则：

1. 有条例码 → 用条码（唯一能真正说明「是不是同一个商品」的字段）
2. 没有条码 → 「品牌 + 归一化名称」；无品牌时只用归一化名称
3. 归一化用 `TextNormalizer.Normalize`（全角转半角、小写、去标点）+ `StripBracketSuffix`：
   `苹果(均值)` 与 `苹果` 算同一条
4. **带品牌的条目只在同品牌内合并**：伊利和蒙牛的「纯牛奶」是两个商品，按名称合并会把
   两家的数值混成一条谁都对不上的记录（E26）
5. **不跨语言合并**：`Apple` 与 `苹果` 是否同一条得靠人判断，机器硬猜会张冠李戴
   （雪梨 / pear / 梨 这类尤其容易错），宁可让用户看到两条

合并后保留优先级最高的那条（先到先得），把其它来源记进 `AlsoFoundIn`，
界面上显示「另见 USDA FoodData Central」。

> 流式上屏时不做跨源合并（增量合并会让先出的那条在后续来源到达时被替换，界面会跳）。
> 每个来源各自成组显示，「另见」只在 `SearchAsync` 的一次性结果里出现。

## 7. 字段与离线结果对齐

`OnlineFoodItem` 的数值字段与 `FoodSummary` 的摘要列一一对应（能量、蛋白、脂肪、碳水、
纤维、糖、钠、钾、钙、胆固醇、GI），单位统一 **每 100 g 可食部**——源那边是「每份」口径的，
由来源自己换算后再交出来。

`NutrientCount` 是有值的项数，用于判断这条数据值不值得采信：只有能量的条目能算热量，
但给不出宏量建议。卡片右下角直接写「6 项数值」，≤2 项时写成「仅 2 项数值」。

## 8. 离线优先与界面接线（T7.4）

首页搜索一次输入会同时发起两条线，谁也不等谁：

```
输入（防抖 220 ms）
   ├─ 离线：IFoodQueryRepository.SearchAsync  → 立即填 Results
   └─ 在线：IOnlineFoodAggregator.StreamAsync → 每回来一个源就填一组 OnlineRows
```

- **离线永远是第一层**：`Results` 排在前面，断网时整页照样能用；在线只是补充
- **在线逐源上屏**：`StreamAsync` 每产出一条就 `ApplyOnlineResultAsync` 一次，慢的那一路不拖住快的
- **代次号 `_onlineGeneration`**：每次新查询加一，旧任务回写一律丢弃。只靠 `CancellationToken`
  不够——取消是协作式的，旧任务可能在取消生效前刚好写一次界面（换关键字时最明显）
- **刷新是逐源的**：在线区标题下面一个来源一行（`OnlineSourceStatusRow`），每行自带一个
  「刷新」按钮走 `RefreshSourceCommand` → `IOnlineFoodAggregator.SearchSourceAsync(key)`，
  只重查那一个源；标题右侧的「全部刷新」才是三源全跑。见 §8.1
- **来源筛选**：`全部 / 离线库 / 各在线源` 一排 chip，chip 上的文字本身就是状态条
  （`离线库 60`、`USDA 失败`、`Open Food Facts 2·缓存`），失败项弱化显示
- **排序只作用于离线结果**：在线结果按各源的相关度排，重排反而打乱它的语义
- **在线卡片**（`OnlineFoodCard`）与离线卡片同一套骨架，多了四样：来源名必有、
  「离线库已有」标记、`英文来源` 标记、右下角「加入本地库」按钮。整卡仍不可点
  （在线条目本身没有本地详情页），左下的「核对来源」打开源站原始条目

### 8.1 单源刷新

三个源失败的原因常常各不相同：USDA 撞了配额、OFF 走了缓存、中文源只是这次没命中。
把它们合成一句「部分来源失败」等于什么都没说，而且用户也没法**只**重试出问题的那一个——
原来的「刷新在线」会把三个源全部重跑，其中两个本来好好的请求被白打一次（中文源是公益站点，
无谓请求要尽量避免）。

现在的做法：

- 每个 `OnlineSourceStatusRow` 自己持有 `IsBusy`，刷新时只有那一行转圈，其余行照常可操作
- 结果回来只替换该源的 `OnlineRows` 分组，其它源的结果一动不动——
  不会因为重查一个源把另外两个的滚动位置和顺序全打乱
- 行的 `DetailText` 就是失败原因（`Hint`），点了刷新之后原地更新，不需要用户自己去找
- `SyncOnlineBusy()` 用 `_onlineRunning` 计数推导全局忙碌态，
  「全部刷新」只在**一个源都没在跑**时可用——单源刷新期间不该把全部刷新也点亮

### 8.2 在线补录：把在线条目转成离线条目

在线条目原本是「只读的结果卡片」：不能加入一餐、不能进冰箱、不能算进日汇总，
因为所有这些功能都要一个 `FoodId`，而在线条目只有「来源 + 远端 id」。

补录（`LocalFoodRecord` / `ILocalFoodStore`）解决这件事，规则是**只增不改**：

| 规则 | 原因 |
|---|---|
| 补录条目落在 `user.db` 的 `local_foods` 表，**从不写进 `food_full.db`** | 离线库是只读的权威数据，混进众包数值就再也分不清哪条可信 |
| id 用**负数**（`-1`、`-2`…） | 正数 id 是离线库的主键区间，负数是「本机补录」的独立命名空间。`IFoodQueryRepository` 见到负 id 就知道该去 `ILocalFoodStore` 查，不需要额外的类型判断 |
| 记住 `SourceKey` + `RemoteId` + `SourceDisplay` | 数据来源必须可追溯：卡片上写「在线补录 · 中国营养学会」，详情页说明里也写明原始出处 |
| 同源同远端 id 走 UPSERT | 同一条重复点「加入本地库」只留一份，不会越点越多 |
| 已补录的卡片换成「已在本机」，点击直接打开本地详情页 | 再点一次没有意义，给一个能到达的下一步 |
| 离线结果里补录条目**排在最前**并带「在线补录」徽标 | 用户刚加完就想看到它；同时徽标保证它不会被误当成权威数据 |

补录进来的条目和离线条目走同一套查询路径：`SearchAsync` 在 `Skip == 0` 时先插补录命中、
`Total` 里加上它们、按当前 `FoodSortMode` 一起排；`GetDetailAsync` 对负 id 走
`GetImportedDetailAsync`（营养素名称与单位取自 catalog，描述里注明出处，同样给同名变体）。
所以「加入一餐」「加入冰箱」「收藏」这些功能对它们全部可用，不需要任何分支。

删除入口有两个：详情页的「删除这条补录」和设置页「在线补录条目」右侧的「清空补录」。
两处都要**点两次**才执行：第一次点只把文案改成「再点一次删除 / 再点一次清空」并给出
6 秒后悔期，第二次才真删。补录条目是用户自己攒下来的，删掉没法从离线库重查回来
（离线库只有同名条目，数值和来源都可能不同），一次误触的代价太大。
应用里没有通用对话框，所以用「按钮自己上膛」实现，不必为这一处引入一个对话服务。
删补录时会连带删掉指向该负 id 的收藏记录，避免留下指向不存在食物的悬空行。


### 「离线库已有」标记

`IFoodQueryRepository.FindExistingNamesAsync` 一次 `IN` 查询回答「这批在线名字里哪些离线库已经有」，
只做归一化同名匹配（去括号、全半角、大小写），**不做模糊匹配**——「苹果汁」不是「苹果」。
命中的在线卡片上标一枚「离线库已有」，因为中文食物绝大多数离线库都覆盖了，
用户多半应该看离线那条（口径是成分表，比众包商品库可靠）。

### 设置页

「在线数据源」卡片按 `IOnlineFoodAggregator.Sources` 自动生成，接新源不需要改界面：

- 每个源一个启用开关（改了就存，不要求再点保存）+ 一个 API Key 输入框
- 每个源「保存」+「测试」两个按钮。**「测试」是 T7.5 之后补上的**：没有它，用户只能回到
  首页搜一次词来判断 Key 填对没填对，而搜索页不会告诉他「是 Key 错了还是这个源本来没有这个词」。
  测试用 `ProbeKeyword` 只取 2 条，结果直接写在该行的说明文字上（`成功 · 2 条 · 412 ms`）
- 要 Key 的源（USDA）在输入框下方给一行「去申请 API Key」链接（`SetupUrl`），
  悬停显示 `SetupHint`——不写清楚去哪儿拿 Key，这个源对普通用户就是死的
- 「结果缓存」一行说明 7 天 TTL，并提供「清空缓存」
- USDA 的 Key 留空时走 DEMO_KEY，卡片上写明「30 次/小时」
- 最下面「在线补录条目」一行：`已有 3 条在线补录…` + 「清空补录」（两步确认）。
  补录是唯一会往 `user.db` 里堆食物数据的入口，必须有一个看得见条数、能一键清空的地方

「本地数据」区块的每个文件 / 目录路径后面都有复制图标（`IconCopy`）：这些路径要拿去
资源管理器或备份脚本里用，靠手抄 `%LOCALAPPDATA%` 下的长路径容易错。
复制走 Avalonia `IClipboard`，成功后按钮下方闪一行「已复制到剪贴板」，失败则提示
「复制失败，请手动选择路径」——静默失败比没有这个按钮更糟。

## 9. USDA FoodData Central

`https://api.nal.usda.gov/fdc/v1/foods/search`，`Order = 20`，`RequiresCredential = false`。

**两个库分开用，先通用后商品。** 通用库（Foundation / SR Legacy）是实验室测定与权威成分表，
商品库（Branded）是厂家标示。按「苹果」直接搜商品库会得到二十条不同品牌的苹果汁，
对用户没有帮助，所以只有通用库一条都没命中时才退到商品库。

**数值按 nutrientId 取，不按名称匹配。** 名称在不同版本里改过措辞
（`Energy` / `Energy (Atwater General Factors)`），ID 是稳定的。能量取 1008（kcal）
→ 2047 / 2048（Atwater 计算值，仍是 kcal）→ 1062（kJ，除以 4.184）；钠、钾、钙、胆固醇
按 `unitName` 判断，给的是 `g` 就 ×1000。

**中文关键字直接返回空。** USDA 里没有中文名条目，实测「苹果」白等 1.5 s 还消耗一次
DEMO_KEY 配额。这条捷径让中文查询的整体耗时从 ~2.5 s 降到 ~1.1 s（只剩 OFF）。

**本地二次排序。** 实测按 `apple` 搜，USDA 自己的相关度前三名是
`Croissants, apple` / `Strudel, apple` / `Babyfood, juice, apple`——全是含苹果的制品，
用户要的苹果本身排在后面。所以请求时放宽到 `take × 4`（上限 50），本地按
「关键字出现位置 → 名称长度」重排后截断。

| 已知限制 | 说明 |
|---|---|
| 网关对 `dataType` 里的括号返回 400 | `Survey (FNDDS)` 无论是否编码都进不来，写成 `Survey` 又匹配 0 条（实测），只能放弃这个数据集 |
| DEMO_KEY 限速 30 次/小时 | 见下面「429 到底是哪种 429」。个人偶尔查够用，密集使用必然撞墙。要长期用得在设置里填自己的 Key |
| 全是英文 | 卡片上标「英文来源」，并把中文名的缺口留给中文源（§11） |

### 9.1 「USDA 一直失败」的定位过程（E38）

现象：用户报「USDA 一直失败，输入 apple 也没有任何结果」，而 OFF 正常。看起来像解析 bug，
实际是**公共 DEMO_KEY 的配额被用光了**。定位靠的是把响应头打出来，而不是猜代码：

```bash
curl -sD - "https://api.nal.usda.gov/fdc/v1/foods/search?api_key=DEMO_KEY&query=apple&pageSize=1"
# HTTP/1.1 429 Too Many Requests
# X-Ratelimit-Limit: 10
# X-Ratelimit-Remaining: 0
# Retry-After: 72874
```

三个信息把问题定死了：

1. `429` 不是 `400`/`403`——请求参数没问题，是**配额**问题
2. `X-Ratelimit-Limit: 10`——共享 DEMO_KEY 实测配额只有 10 次/小时，文档上写的 30 次是乐观值
3. `Retry-After: 72874`（约 20 小时）——统计窗口是滑动小时且全世界的匿名调用者共用一个池，
   撞上之后基本等于当天没得用

原来的代码把 429 统一收成「达到限速上限，请稍后再试」：技术上没错，但对用户毫无用处——
他并不知道「稍后」是 20 小时后，也不知道自己能立刻解决。现在的处理：

| 做法 | 原因 |
|---|---|
| DEMO_KEY 与自有 Key 的 429 **分开写文案** | 自有 Key 撞 429 是「你自己的配额用完了，等一小时」，DEMO_KEY 是「公共池被用光了，填自己的 Key 就能立刻恢复」。两句话指向完全不同的动作 |
| 读 `Retry-After` **本地冷却**（上限 1 小时） | 冷却期内直接抛异常、连请求都不发。没有这一步，用户每敲一个字都白打一次请求，界面上一串红色失败，还可能因为持续违规把 IP 也带进去 |
| 冷却只对 DEMO_KEY 生效 | 用自己的 Key 撞 429 不该被锁死——那是用户自己的配额，等一分钟就能继续试 |
| 失败文案里给 `SetupUrl` | 「去申请 API Key」是可点的，用户不必自己去搜 USDA 官网 |


## 10. Open Food Facts

`https://search.openfoodfacts.org/search`（Search-a-licious）+ `api/v2/product/{条码}.json`，
`Order = 30`，免 Key。

**检索不用老的 `/cgi/search.pl`。** 老接口从几百毫秒到十几秒随机，很容易撞上 8 s 超时；
新接口实测 1 s 级返回，且支持 `fields` 只取需要的字段（整条产品对象有上百个字段）。

**单位换算是这个源最容易错的地方。** OFF 的 `*_100g` 全部是「每 100 g 的克数」，矿物质也不例外：
钠 `0.0428` 表示 42.8 mg，不 ×1000 就会显示成 0 mg。缺 `sodium_100g` 时从盐换算（钠 = 盐 / 2.5，
即 `salt_100g × 400` mg）。缺 `energy-kcal_100g` 时用 `energy-kj_100g / 4.184`，
老字段 `energy_100g` 也是 kJ。

**众包噪声要挡在源头。** 只填了名字、没有任何营养数据的条目直接丢弃——它在搜索结果里
只会占一个位置，还会让用户以为「这东西没热量」。名称字段可能是字符串也可能是
`{"zh": "…", "en": "…"}`，品牌在检索接口是数组、在商品接口是逗号分隔字符串，都要容错。

## 11. 中文源：中国营养学会（T7.5，已上线）

中文用户最需要的其实是这一个源：离线库的数值本来就出自《中国食物成分表》，在线再查到
同源的条目，口径和习惯都对得上。它长期被当作「没有公开 API」，2026-10-22 实测后的结论不同：
**列表查询其实是 JSON，可以直接做。**

### 11.1 `nlc.chinanutri.cn/fq/` 接口实测

列表接口（**POST，form-urlencoded**，不需要任何鉴权 / Cookie）：

```
POST https://nlc.chinanutri.cn/fq/FoodInfoQueryAction!queryFoodInfoList.do
     categoryOne=0&categoryTwo=0&foodName=苹果&pageNum=1&field=0&flag=0
```

返回：

```json
{"currentPage":"1","totalPages":4,
 "list":[[613,"","苹果(均值)","","","76%","85.9g","229kJ","0.2g","0.2g","","0.2g",
          "13.5g","","20.0μg","","—","0.06mg","0.02mg","0.20mg","4.0mg","4mg","12mg",
          "119mg","1.6mg","4mg","0.6mg","0.19mg","0.10μg","0.06mg","0.03mg","","—","—","—","—"]]}
```

**`list` 里是「数组的数组」，没有字段名**，只能靠位置对。用「苹果(均值)」这一行
（成分表第 6 版公开数据）逐位比对，能确定的位置是：

| 位置 | 含义 | 位置 | 含义 |
|---|---|---|---|
| 0 | 记录 id（详情页要用） | 17 | 硫胺素 mg |
| 2 | 名称 | 18 | 核黄素 mg |
| 5 | 可食部 % | 19 | 烟酸 mg |
| 6 | 水分 g | 20 | 维生素 C mg |
| 7 | 能量 **kJ** | 21 | 钙 mg |
| 8 | 蛋白质 g | 22 | 磷 mg |
| 9 | 脂肪 g | 23 | 钾 mg |
| 10 | 胆固醇 mg | 24 | 钠 mg |
| 11 | 灰分 g | 25 | 镁 mg |
| 12 | 碳水化合物 g | 26 | 铁 mg |
| 13 | 总膳食纤维 g | 27 | 锌 mg |
| 14 | 胡萝卜素 μg | 28 | 硒 μg |
| 15 | 维生素 A μg | 29 / 30 | 铜 / 锰 mg |
| 16 | **α-TE（维生素 E）mg** | 31 | **碘 μg** |
| — | — | 32–35 | 脂肪酸构成：饱和 / 单不饱和 / 多不饱和 / 合计 **%** |

- 校验方式：苹果 229 kJ ÷ 4.184 = 54.7 kcal（成分表标 54），钙 4 / 磷 12 / 钾 119 / 钠 1.6 全部对得上
- **13 位是总膳食纤维**：苹果、黄豆这一栏是空的，但燕麦片取到 `13.20g`、番杏 `2.60g`，
  与成分表一致——普通食物大多不填，空就留 null
- **16 位是 α-TE，也就是维生素 E**（mg）。它紧跟维生素 A，很容易被当成「视黄醇」那一类 μg；
  番杏写的是 `0.20mg`，单位对不上 μg 才反应过来
- **31 位是碘，不是维生素 E**。原以为「矿物质末尾该跟维生素 E」，拿番杏（`0.9μg`）一对就露馅：
  维 E 是 mg，不可能出现 μg；回详情页逐行对齐，第 31 行写的是「碘(I)」（E40）
- 32–35 是脂肪酸**构成比**（百分数），不是克数，对不上任何 `*_g` 字段，所以不读
- 能量给的是 kJ，要 ÷ 4.184 换成 kcal；单位混在字符串里（`g` / `mg` / `μg` / `%`），要按后缀解析
- `"—"` 表示未测，空串表示不适用，`"Tr"` 表示微量（按 0 处理或留空）

**核对手段**：列表接口没有字段名，但详情页 `foodinfo/{id}.html` 是服务端渲染的表格，
带中文 + 英文标签（`碘(I)`、`总膳食纤维(Dietary fiber)`），把它的 `<td>` 按顺序抽出来
就能给列表接口的每一列「贴标签」。这种对齐只要做一次，之后任何一列的疑问都能回查。


详情页是**服务端渲染的 HTML**，没有 JSON；要拿全量营养素（含各类脂肪酸、胆固醇细分）
只能解析 HTML 表格。**但首页搜索不必碰它**——列表接口已经给到能量、三大宏量、纤维、
钠钾钙磷镁铁锌硒铜锰碘和维生素 A/E/B1/B2/B3/C，足够卡片展示与「加入一餐」的粗算。
详情页只在 `GetAsync`（按 id 取详情）时才碰。

### 11.2 落地（已完成，T7.5）

`ChinanutriFoodSource`，`Key = chinanutri`，`Order = 10`，`RequiresCredential = false`：

| 项 | 做法 | 原因 |
|---|---|---|
| 请求 | `POST` + `FormUrlEncodedContent`，带 `Referer` 与常见 `User-Agent` | 站点是公益性质，伪装成浏览器的正常访问比空 UA 更不容易被拦 |
| 分页 | 只打 `pageNum=1`，本站每页固定 8 条、**没有 pageSize 参数** | 一次要 6 条足够，多取只能翻页，对站点是不必要的压力 |
| 解析 | `JsonDocument` 取 `list`，逐行按索引读，字符串按后缀（`g`/`mg`/`μg`）换算单位 | 顺序固定，无需猜字段名 |
| 缺失值 | `""` 与 `"—"` → `null`；`"Tr"`（微量）→ 0 且不进字典 | 「没测」和「是 0」必须分开：写成 0 会让日均摄入算错 |
| 关键字 | 中文直接查；**英文关键字直接返回空，不发请求** | 站内没有英文名条目，发出去只会白等 1.5 s |
| URL | `https://nlc.chinanutri.cn/fq/foodinfo/{id}.html` | 卡片「核对来源」直接打开原始条目 |
| 额外营养素 | 进 `OnlineFoodItem.ExtraNutrients` | 补录落库以后，详情页才有完整的表可看 |
| 「离线库已有」 | 会命中得比较多 | 它和离线库同源（成分表第 6 版），命中说明用户看离线那条更合适 |

**没有做的两件事**：① 请求节流（每次 ≥ 500 ms）——目前靠 220 ms 防抖 + 7 天缓存挡，
搜索是用户手打触发的，实际频率远低于节流阈值；真出现刷站再补。
② 批量镜像/预抓——**不做，也不该做**。定位始终是「用户主动搜一个词，展示几条结果并标注来源」。
