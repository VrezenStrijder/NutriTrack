# 数据结构说明

> 适用版本：派生成分库 schema_version = 1 · 用户库 schema v11（2026-10-27）
> 三层数据：**源库（只读）→ 派生成分库（只读）→ 用户库（可写）**

---

## 一、三层数据总览

| 层 | 文件 | 读写 | 管理者 | 说明 |
|---|---|---|---|---|
| 源库 | `data/food_composition.db` | 只读，**永不修改** | 人工整理 | 16 个数据集的原始导入结果，作为唯一事实来源 |
| 派生成分库 | `data/generated/food_full.db`<br>`data/generated/food_core.db` | 只读 | `tools/fooddb/build_food_db.py` 生成 | 营养素归一化后的查询库；两库 **schema 完全一致**，只有行数范围不同 |
| 用户库 | `%LOCALAPPDATA%/NutriTrack/user.db`<br>（Android：应用私有目录） | 读写 | 应用运行时 | 用户档案、收藏、用餐记录、查询历史、在线补录与自建菜品；EF Core 管理 |

设计要点：

- **源库不动**。所有清洗、归一、补录都发生在派生层，源库损坏可以随时重建。
- **派生库只读**。用 `Mode=ReadOnly` 连接，避免运行时误写破坏一致性。
- **两库同构，但 core 少一张表**。`food_full.db`（44,688 条，含 USDA/日本/中国/台湾/香港/补充/菜品）与 `food_core.db`（7,648 条，仅中国+台湾+香港+补充+在线补录）的 `food` / `food_nutrient` / `food_alias` 等表结构、字段语义、索引完全相同，查询层不需要分支。差异只有一处：菜品（2 万条）连同 `dish_ingredient` 只进 full 库——它会把 core 的体积从 9.5 MB 撑到 93 MB 左右，而移动端首版不需要。因此详情页读配料时对「表不存在」做了容错，退化为不显示配料（见 `docs/08-菜品数据说明.md` §5.2）。core 里的 229 道港式熟食来自香港 CFS，是实测值、不带配料表，不受这条限制。切换方式：`FoodDatabaseLocator` 按候选路径依次探测，或设置环境变量 `NUTRITRACK_FOOD_DB`。

### 1.1 用户库里的两类敏感字段（2026-10-27）

**头像**（`users.AvatarKind` / `users.AvatarValue`，schema v11）

| 字段 | 取值 |
|---|---|
| `AvatarKind` | `0` 默认头像 · `1` 图案头像（新档案与升级上来的老档案都用它）· `2` 上传照片 |
| `AvatarValue` | 默认头像：配色下标（0–7）<br>图案头像：种子，留空时按昵称算<br>照片：`%LOCALAPPDATA%/NutriTrack/avatars/<guid>.png` 的文件名 |

图案本身**不入库**：`Core/Avatars/AvatarPattern` 用 FNV-1a 从种子算出 5×5 左右对称网格与色相，
同一昵称在任何机器上都长一样，因此老档案升级不需要逐行回填。照片只存文件名，图片本体在
`avatars` 目录里，也不进备份包（跨机器导入后读不到文件，界面自动退回图案头像）。

**凭据**（`vision_providers.ApiKey`、`app_settings` 里的 `online.*.api_key`）

落盘即密文，形态为 `enc:v1:<Base64>`。Windows 用 DPAPI（当前用户作用域 + 固定熵），
其它平台用 `secrets.key` 密钥文件 + AES-GCM。加密解密只在仓储层做，上层拿到的永远是明文；
启动时 `SecretMigration` 把加密功能上线前的历史明文补一次（幂等）。
设置表里除 `*.api_key` 之外的值（主题、字号、折叠状态）不加密——它们不是凭据，
加密只会让用户自己看不懂配置文件。

### 1.2 设置表的键位约定（2026-10-29）

`app_settings` 是一张 `key` / `value` 的键值表，键名用前缀分组。加新前缀前先看这张表——**哪些能进备份、
哪些必须留在本机**，靠前缀就能判断：

| 前缀 | 用途 | 进备份包 |
|---|---|---|
| `ui.*` | 界面偏好：`ui.theme`、`ui.font_scale`、`ui.accent`、`ui.nav_collapsed`、`ui.close_to_tray`、`ui.tray_hint_shown`、`ui.advice_*_expanded`、`ui.window_width` / `_height` / `_x` / `_y` | 是（换台机器版式不重调） |
| `reminder.enabled` / `reminder.meal_enabled` / `reminder.meal_time` / `reminder.weight_*` | 提醒的用户设置 | 是 |
| `reminder.meal_prompt_on.u{id}` / `reminder.weight_prompt_on.u{id}` | **运行时状态**：某个档案某种提醒「最后提醒过哪一天」 | **否**，导出时按 `reminder.` + `_prompt_on` 剔除 |
| `online.*.api_key` | 在线数据源密钥 | 是（默认带、可取消；落盘加密） |
| `backup.auto_enabled` / `backup.auto_last_at` | 自动备份开关与上次执行时间 | 是（`auto_last_at` 跟着走也无害：另一台机器的下一次判定只会更早，不会更晚） |

两条规则：

- **按档案分开记的东西，键里必须带 `u{id}`。** 提醒记账原来存在 `ReminderSettings` 里（全局一份），
  两成员切换时互相顶掉——甲早上称了体重，乙当天就收不到提醒。`users.id` 会被 SQLite 复用，
  所以删档案时由 `ReminderSettingsStore.ClearPromptsOf` 一并清掉，否则新成员会继承「今天提醒过」。
- **窗口几何进备份但 `SameAs()` 不比较它。** 它是「这台机器的屏幕」的属性，不是用户偏好；
  还原到另一台机器时尺寸会被工作区钳制（`ApplyWindowPlacement`），位置不在任何屏幕上就回落到居中。

## 二、派生成分库 Schema

### 2.1 `food` — 食物主表

| 字段 | 类型 | 语义 | 备注 |
|---|---|---|---|
| `food_id` | INTEGER PK | 主键 | 继承源库 `food.food_id`；在线补录条目从 `900000` 起，与源库隔离 |
| `name` | TEXT | 规范名 | 简体中文优先；USDA/日本数据为原文 |
| `name_original` | TEXT | 原始名 | 繁体/英文/日文原文，用于溯源 |
| `name_norm` | TEXT | 检索用归一化名 | NFKC + 小写 + 去空白标点，见 `TextNormalizer.Normalize` |
| `name_key` | TEXT | 同名分组键 | 当前等于 `name_norm`；同名跨源条目共享同一 `name_key` |
| `variant_key` | TEXT | **变体组键** | 同一件食物的不同叫法（`番茄` / `西红柿` / `番茄[西红柿]`）共用一键。菜品加 `dish\|` 前缀，不与食材混组，见 §5.5 |
| `canonical_id` | INTEGER | 代表行指针 | **变体组**里被选中的代表条目；查询默认只取 `food_id = canonical_id` 的行 |
| `variant_count` | INTEGER | 组内条目数 | 只写在代表行上；1 表示独条 |
| `variant_energy_min` / `_max` | REAL | 组内能量范围 | 只写在代表行上，用于「同名 3 条 · 22–328 kcal」提示；缺能量时为 NULL |
| `py_full` / `py_initials` | TEXT | 拼音全拼 / 首字母 | 支持 `pingguo`、`pg` 检索；非中文名为空 |
| `group_key` | TEXT | 统一分类键 | 15 类，见 §4 |
| `group_display` | TEXT | 原始分组名 | 中国/台湾为中文名，USDA 为英文名 |
| `source_key` | TEXT | 数据源标识 | `ds1`…`ds16`，本地补充 `ds97`/`ds98`，在线补录 `ds99`，香港 CFS `cfs` |
| `source_display` | TEXT | 数据源展示名 | 如「中国食物成分表」 |
| `source_food_id` | TEXT | 源库原始 id | 可回溯到源库精确记录 |
| `source_priority` | INTEGER | 来源优先级 | 数字小优先：中国 10 < 在线补录 15 < 台湾 20 < **香港 25** < 日本 30 < USDA 40 < 菜谱 60 |
| `edible_pct` | REAL | 可食部百分比 | 如 82 表示 100 g 中有 82 g 可食 |
| `region` | TEXT | 适用地区 | 中国大陆 / 中国台湾 / 中国香港 / 美国 / 日本 |
| `nutrient_count` | INTEGER | 已归一营养素项数 | 用于排序与质量判断 |
| `description` | TEXT | 说明 | 补录条目记录来源关键词与平台链接 |
| `energy_kcal` 等 10 列 | REAL | 常用营养素冗余列 | 列表页与排序直接取用，免 join；**权威值仍在 `food_nutrient`** |
| `gi` | REAL | 血糖生成指数 | 可空。**不进 `food_nutrient`**——GI 没有单位、也不是「每 100 g 含量」，而是相对葡萄糖=100 的比值，见 §5.2 |
| `glycemic_load` | REAL | 血糖负荷 | 可空。`GI × 可利用碳水 / 100`，与 `gi` 同时有值或同时为空 |
| `gi_source` | TEXT | GI 出处 | 「中国食物成分表」「glycemic-index.net」「health.db」「国际GI表2008」「人工校准」 |
| `external_url` | TEXT | 官方详情页 | 中国营养学会平台 `foodinfo/{id}.html` |

**冗余列清单**：`energy_kcal`、`protein_g`、`fat_g`、`carb_g`、`fiber_g`、`sugar_g`、`sodium_mg`、`potassium_mg`、`calcium_mg`、`cholesterol_mg`。

> 冗余是刻意的：一页 60 条列表若逐条 join `food_nutrient`（66 万行）在移动端会明显掉帧。冗余列只用于**展示与排序**，计算营养目标达成率时仍走 `food_nutrient`。

### 2.2 `food_nutrient` — 营养素长表

| 字段 | 类型 | 语义 |
|---|---|---|
| `food_id` | INTEGER | 外键 → `food.food_id` |
| `nutrient_key` | TEXT | 规范营养素键，见 §3 |
| `amount` | REAL | 每 100 g 可食部的含量，单位由 `nutrient_catalog.unit` 决定 |

主键 `(food_id, nutrient_key)`，`WITHOUT ROWID`。**一个食物一个营养素只有一条记录**，多来源冲突在构建期按「优先级 + 值状态可信度」消解，不保留多值。

### 2.3 `nutrient_catalog` — 营养素目录

| 字段 | 语义 |
|---|---|
| `key` | 规范键，如 `vitamin_c_mg` |
| `name_cn` / `name_en` | 中英文名 |
| `unit` | **规范单位**，全库统一 |
| `category` | `macro` / `lipid` / `mineral` / `vitamin` / `other`，决定明细页分组 |
| `sort` | 展示顺序 |
| `ref_daily` | 参考日摄入量（成人均值），仅用于「占比」进度条，**不是个体化建议** —— 个体化目标由 `TargetCalculator` 按 DRI 表计算 |

### 2.4 `food_alias` — 通用名别名

| 字段 | 语义 |
|---|---|
| `alias` | 归一化后的通用名，如 `三文鱼` |
| `food_id` | 指向的代表条目 |

主键 `(alias, food_id)`。三类来源，优先级从高到低：

1. **同义词词典**（`tools/fooddb/synonyms.py`）——「三文鱼→鲑鱼」「鸡胸肉→鸡胸脯肉」「牛油果→鳄梨」。这是**命名差异**，不是数据缺失。
2. **自动别名**——去掉名称末尾方括号补充说明：「中华猕猴桃[毛叶猕猴桃]」→「中华猕猴桃」。
3. **通用名启发**——「苹果」在库里只有品种条目时，按「完全同名 → 含平均/均值 → 名称最短 → 营养项最多」挑代表。

`BLOCKED_TERMS` 里的词（如「鸡肉」）**故意不建别名**：库里只有「火鸡肉」等条目，硬指一条会误导，让用户走文本匹配自己挑。

### 2.5 `meta` — 元信息

`key` / `value` 键值对：`schema_version`、`built_at`、`scope`（all/core）、`datasets`、`food_count`。

### 2.6 `dish_ingredient` — 菜品配料组成

| 字段 | 类型 | 语义 |
|---|---|---|
| `dish_food_id` | INTEGER | 菜品 id（对应 `food.food_id`，900000 起） |
| `seq` | INTEGER | 菜谱里的原始顺序 |
| `name` | TEXT | 配料名，保留菜谱原样（「草鱼一条」也好，解析失败照样留） |
| `grams` | REAL | 折算后的克数；算不出为 0 |
| `food_id` | INTEGER | 匹配到的成分表条目；未匹配为 0 |
| `match_kind` | TEXT | `exact` / `alias` / `synonym` |

详情页据此说明「这个数字是拿什么算的」。只有菜品行有配料，普通食物这张表里没有记录。

## 三、规范营养素（41 项）

单位是全库约定，**跨库对比前不需要再换算**。

| 分类 | 键 | 中文名 | 单位 |
|---|---|---|---|
| 能量与宏量 | `energy_kcal` | 能量 | kcal |
| | `water_g` `protein_g` `fat_g` `carb_g` `fiber_g` `sugar_g` `ash_g` | 水分/蛋白质/脂肪/碳水/膳食纤维/糖/灰分 | g |
| 脂类 | `saturated_fat_g` `monounsaturated_fat_g` `polyunsaturated_fat_g` `trans_fat_g` | 饱/单不饱/多不饱/反式脂肪 | g |
| | `cholesterol_mg` | 胆固醇 | mg |
| 矿物质 | `sodium_mg` `potassium_mg` `calcium_mg` `magnesium_mg` `phosphorus_mg` | 钠/钾/钙/镁/磷 | mg |
| | `iron_mg` `zinc_mg` `copper_mg` `manganese_mg` | 铁/锌/铜/锰 | mg |
| | `selenium_ug` `iodine_ug` | 硒/碘 | μg |
| 维生素 | `vitamin_a_ug` `retinol_ug` `carotene_beta_ug` `vitamin_d_ug` `vitamin_k_ug` | 维A/视黄醇/β-胡萝卜素/维D/维K | μg |
| | `vitamin_e_mg` `thiamin_mg` `riboflavin_mg` `niacin_mg` `pantothenic_acid_mg` `vitamin_b6_mg` `vitamin_c_mg` `choline_mg` | 维E/B1/B2/烟酸/泛酸/B6/C/胆碱 | mg |
| | `biotin_ug` `folate_ug` `vitamin_b12_ug` | 生物素/叶酸/维B12 | μg |
| 其他 | `caffeine_mg` `alcohol_g` `salt_equivalent_g` | 咖啡因/酒精/食盐当量 | mg / g / g |

**换算规则**（构建期一次性完成）：
- 能量：`kJ ÷ 4.184 = kcal`；中国库的「千卡」直接采用
- 质量：`μg ÷ 1000 = mg`，`mg ÷ 1000 = g`
- 无法确定单位来源的值**直接丢弃**，绝不做猜测换算

原始库 941 条营养素定义中 219 条被映射；未映射的 722 条是氨基酸、单个脂肪酸、单糖等细分项，属设计内省略——需要时可回源库按 `source_food_id` 查。

## 四、统一分类（15 类）

`grain` 谷物薯类 · `bean` 豆类及制品 · `vegetable` 蔬菜 · `fruit` 水果 · `meat` 畜禽肉 · `aquatic` 水产 · `egg` 蛋类 · `dairy` 奶类 · `nut` 坚果种子 · `oil` 油脂 · `bakery` 糕点甜食 · `beverage` 饮料 · `condiment` 调味品 · `processed` 加工食品 · `other` 其他

映射顺序（`nutrient_map.resolve_group`）：

1. 精确表 `GROUP_MAP`——覆盖中文（中国/台湾分组名）、英文（USDA）、日文（MEXT 18 个大类编码 `01`–`18`）
2. 英文词首匹配——`\bvegetable` 能命中 `Vegetables and...`，又不会把 `steak` 判成 `tea`
3. 中文关键字兜底——蔬/菜/果/肉/鱼/蟹/蛋/乳/豆/谷/麦/米/面…
4. 仍未命中归 `other`，构建日志会打印未识别分组名，便于补表

### 5.1 本地补充数据（`data/additional/`）

除源库外，还有一批人工整理的补充数据，构建时并入两个库：

| 文件 | 条数 | 内容 | 归入数据集 |
|---|---|---|---|
| `foods.csv` | 1,677 | 第 6 版中国食物成分表完整导出，36 列 | `ds15` |
| `add2.csv` | 194 | 精简 7 列，糖类、面条细分类、调味品 | `ds98` |
| `add3.csv` | 42 | 罕见蔬果与野菜（巴婆果、蜂王浆、酸模等） | `ds98` |
| `add1.json` | 1 | 单条手工成分表（喷瓜） | `ds97` |

并入策略是**只补不覆盖**：

- 同名（`name_norm` 相同）已存在时，只往缺失的营养素键里填值，已有值一律保留
- 例外：已有值为 `0` 而新值 `> 0` 时允许覆盖。源库把「没测」写成了 0（薤的 25 项数据里能量是 0 kcal），这种 0 不是实测结果
- 被补过的行会重算摘要列与 `nutrient_count`，否则详情页顶部卡片会空着、搜索排序权重也会失真

构建输出：
```
[all] 本地补充: 新增 1061 条，补全 786 条
```

**为什么不改这些数值**：构建时会对宏量做自洽检查（`4P + 9F + 4C` 与标示能量的偏差），但**只报告不修改**。第 6 版的能量多为实测值，公式对两类食物必然失效——含酒精的（酒精 7 kcal/g，公式没这一项，啤酒会被算成 16 kcal）和高纤维的（CHO 口径与膳食纤维重叠时 4×C 高估，稻麸会被算成 440 kcal）。当前有 40 条被标记待复核，原样保留。

**分类修正**：补充数据里 `resolve_group` 兜不住的名字（野菜、葡萄、薯条、香草）走一层 `_GROUP_REFINE` 修正，**只作用于归到 `other` 的条目**，已分对的一律不动。修正后新增条目里 `other` 只剩 17 条，全是蜂产品（蜂王浆、蜂胶、蜂蛹）与药食（阿胶、牛黄、燕窝、龟甲、蛤蚧），与第 6 版「药食及其它」的归类一致。

### 5.2 血糖生成指数与血糖负荷

由 `tools/fooddb/gi_sources.py` 完成，四源合并后写入 `food.gi` 与 `food.glycemic_load`，来源记在 `food.gi_source`。

> **本节仅列数据口径；源的取舍、被排除的两份网页数据、匹配算法与已知局限见 `docs/07-血糖数据说明.md`。**

**为什么单独一列而不是 `food_nutrient`**：`food_nutrient` 的语义是「每 100 g 可食部的含量」，单位由 `nutrient_catalog.unit` 决定。GI 是相对值（葡萄糖 = 100），没有单位，也不随份量线性缩放——塞进长表会污染营养素的排序与每日参考值计算。GL 同理。

**GL 一律用库内碳水重算**：`GL = GI × max(0, carb_g − fiber_g) / 100`。不采信数据源自带的 GL——那是按各家碳水口径算的，直接采用会出现「碳水 20 g、GL 15」这种读不通的组合。

**匹配三级策略**：

| 级 | 规则 | 说明 |
|---|---|---|
| 1 | 归一化后精确同名 | NFKC + 去标点 |
| 2 | 去括号取主名（`米饭(蒸)(均值)` → `米饭`） | 主要来源；主名冲突则放弃 |
| 3 | 英文词集相等（`Milk, whole` ≈ `Whole milk`） | 只用于英文条目，多值则放弃 |
| 4 | 人工校准（命名分歧） | 优先级 0，不被批量匹配覆盖 |

第 2 级有两个坑，都踩过：

- **主名表必须连「本来就没括号」的条目一起收。** 早先只收带括号的条目，结果 `苹果(均值)` 去括号得到 `苹果`，而 GI 表里的 `苹果` 自己没括号所以不在表里——最常见的水果反而查不到 GI。
- **同一主名下互相矛盾的 GI 不能取均值。** `大米饭（籼米，精米）`82 与 `大米饭（粳米，精米）`90 差 8 点，合并等于造一个库里不存在的「混合米饭」。现在的优先级是：本来就没括号的那条 > 所有细分条目一致 > 放弃。

**两道硬过滤**：`GI <= 0` 或 `> 150` 丢弃（glycemic-index.net 把纯油脂记成 0）；`carb_g < 1` 不挂（碳水近零时 GI 无解释力，阈值取 1 是为了保住牛奶的 3.4 g）。

**明确的排除项**：`枣`、`米` 不参与主名匹配——鲜枣与干枣的 GI 差得远，`米` 会连带 `米粉`（见 `_BASE_AMBIGUOUS`）。

覆盖率（代表行口径）：**full 1,054 / 43,071（2.4%），core 941 / 6,586（14.3%）**；把同名来源行也算上是 1,383 / 44,688 与 1,262 / 7,648。绝大多数食物没有实测 GI，这是数据源的边界，不是匹配失败——`胡萝卜`、`豆浆` 在整个 GI 表里就没有条目。

**分级口径**：低 < 55、中 55–70、高 > 70（中国食物成分表口径），落在 `FoodSummary.GiLevel`。

### 5.3 菜品（家常菜与份量）

由 `tools/fooddb/dish_recipes.py`（HowToCook）、`dish_xcf.py`（下厨房语料）、`dish_build.py`（合并去重）三步完成。

- 数据源：HowToCook 353 篇（带「计算」区块的配料克数）+ 下厨房语料 148 万条（补菜名覆盖）
- 折算：配料克数 × 成分表每 100 g 含量 → 加权求和 → 除以成品总重（油炸按吸油率加回）
- 闸门：主料未定量 / 主料未匹配 / 匹配配料 < 3 项 / 质量覆盖率 < 75% / 能量不在 10–750 kcal·100g⁻¹，任一命中即拒绝
- 产出：**20,229 条** `group_key='dish'`（菜谱推算 20,000 + 香港 CFS 港式熟食 229），`dish_ingredient` **182,692 行**；HowToCook 过闸门 160/353（45%），语料全量扫出 109,966 道合格菜品后按覆盖率取前 19,840
- 货号段 `900000–949999`；`source_priority` 60/61，低于所有实测成分表

> 口径、单位换算表、件数表、被拒原因与已知局限见 `docs/08-菜品数据说明.md`。

**为什么不能拿作者的「预估卡路里」当校验**：作者标的是整锅，我们算的是整份，口径不同——第一版用它做 40% 偏差闸门，把「清蒸鲈鱼」这类正确答案也拦掉了。现在只写进 `description` 供人对照，判据改成绝对区间。

**为什么不追求覆盖率 100%**：「适量」「少许」「一把」没有克数，只能丢弃并计入覆盖率；覆盖率不够就整条拒绝，而不是按 0 补——补 0 会把一道菜稀释成葱姜水。

### 5.4 香港食物安全中心（`data/cfs_food_nutrients.csv`）

香港食安中心《食物营养成分资料库》的简体转写版，3,206 行、固定每 100 克给值，由 `tools/fooddb/cfs_import.py` 读入。

- **只有 10 项营养素**：能量、蛋白、脂肪、碳水、膳食纤维、糖、饱和脂肪、反式脂肪、胆固醇、钠。没有维生素与矿物质细分，缺的项不补、不猜。
- **非数字标记**：`NA`（未测定）跳过；`ND`（未检出）、`Trace`（微量）、`<2.5`（低于检出限）按 0 计——与源库 `stream_nutrients` 对 `trace / below_loq / not_detected` 的口径一致，不搞两套规则。全表共 6,510 个 `NA`。
- **分类映射**：26 个「食物类别」→ 15 个 `group_key`。`本地粥粉面饭`、`本地早餐`、`本地中式点心`、`汤类` 归 `dish`（这些是港式熟食，不是食材）；`即食食物`、`小食`、`婴儿食品` 归 `processed`；其余按食材归 `grain`/`meat`/`aquatic` 等。
- **同名去重**：3,206 行里有 279 行是重复条目——同一食物既按「食物类别」出现一次、又按「本地xxx」专题出现一次（如「占酱多」同时在「谷类及制品」和「本地早餐」），或来自两个资料源（「蚝(生)」A 源 51 kcal、D 源 64 kcal）。按归一化名只留一条：**年份新的优先 → 营养项多的优先 → 先出现优先**；分类单独取更具体的那个，所以「占酱多」会落在 `dish` 而不是 `grain`。最终入库 **2,927 条**。
- **年份后缀**：资料库给部分条目加了化验年份（`菠萝包 (2002)`、`叉烧肠粉 (2021)`）。年份只写进 `description`，不进名称——留在名称里会与成分表的「菠萝包」判成不同名，错过同名合并，实测值就顶不掉菜谱推算值。
- **别名**：`别名` 列的 `[干瑶柱]`、`[带子]、[鲜贝]` 拆开写进 `food_alias`（633 条，实际生效 197 条），不拼进名称。搜「凤梨」能出「菠萝包」，搜「干瑶柱」能出成分表的「扇贝(干)[干贝]」。
- **与菜谱的关系**：优先级 25 vs 菜谱 60，同名时 CFS 的实测值成为代表行。这也是「麻婆豆腐」从日本表的 104 kcal 变成 130 kcal 的原因——`docs/06` 里那条数据缺口由这批数据补上了。

### 5.5 变体聚合：同名异义与异名同义

成分表里同一件食物常常有三条记录：`番茄[西红柿]`（中国食物成分表）、`番茄`（香港 CFS）、`西红柿`（下厨房语料）。反过来，同一个名字下也可能藏着两种完全不同的东西：`绿茶` 既是干茶（328 kcal/100 g），也是茶汤（22 kcal/100 g）。

`tools/fooddb/variants.py` 在重建时给每条食物算 `variant_key`，规则只有两条：

1. **方括号别名**：中国食物成分表的 `正名[别名，别名]` 写法，剥掉末尾 `[...]` 得到正名。**圆括号一律不剥**——`菜花(脱水)[脱水花椰菜]` 里的「脱水」是形态，剥掉就会和新鲜菜花（24 kcal）混成一条。
2. **同义词组表**（79 组）：`("马铃薯", "土豆", "洋芋")` 这类确知同物的叫法。词典里只放拿得准的，「地瓜」这种既可能指甘薯也可能指豆薯的词不收。

**代表行选择**：来源优先级 → 营养项多 → `food_id` 小。与旧的同名规则一致，只是分组口径从 `name_key` 换成 `variant_key`。菜品（`group_key='dish'`）加 `dish|` 前缀，不与食材混组：语料里确实有一道菜就叫「香菇」，那是炒香菇，不是干香菇。

**同名异义不靠猜，靠展示**：组内能量差 ≥ 30 kcal 且 ≥ 20% 时，列表卡片显示「同名 3 条 · 22–328 kcal」，详情页逐条列出并标注「低 274 kcal」，点一行直接切过去。干茶/茶汤、干扁豆/鲜扁豆这类情况，替用户选等于替他猜。

**顺带清掉的假菜**：语料里有 5 条「菜」的名字就是食材本身（西红柿、里脊肉、香菇、芒果、蜜麻花），留着会在同名检索里把真正的食材挤到后面。构建时若菜名命中已有食材的变体键，整条丢弃（`dish_build.py`），名额由后面的候选补上。

**别名指向组代表**：搜「西红柿」「土豆」「凤梨」都会落到组内代表行。词典里的组名优先于方括号别名——`奶柿子[西红柿]` 是一条具体的番茄品种，不能把「西红柿」这个通名抢走。

> 结果：代表条目 43,071 → **43,018**（53 条被同义合并）；**1,481** 个组有 2 条以上成员，其中 **140** 组能量差 > 30 kcal；别名表 3,081 条（其中「变体组」来源 433 条）。

### 5.6 食谱库（`data/GI/health.db`）

健康管理侧的 SQLite 库，里面除了用户、饮食记录，还有两张可复用的表：

| 表 | 字段 | 用法 |
|---|---|---|
| `recipes` | `recipe_id`、`recipe_name`、`description`、`calories`、`protein`、`fat`、`carbs`、`fiber`、`tags` | 25 条家常菜，能量与三大营养素按**一份**计（不是每 100 g） |
| `recipe_ingredients` | `recipe_id`、`ingredient_name`、`amount`、`unit` | 每道菜的配料与用量，如「鲈鱼 1 条」「姜片 10 g」 |

- 只读接入：`IRecipeRepository` / `SqliteRecipeRepository`，路径由 `RecipeDatabaseLocator` 按「环境变量 `NUTRITRACK_RECIPE_DB` → 应用数据目录 → 输出目录 → 仓库 `data/GI`」查找，找不到时 `IsAvailable = false`，建议页不显示「推荐食谱」卡片；
- 选择规则在 `Core/Advice/RecipeMatcher`：把档案翻译成想要的标签（糖尿病 → 糖尿病 + 低GI，减脂 → 减脂，孕期 → 孕妇，≥65 岁 → 老年人 …），命中越多权重越高；命中 0 的菜不出现；
- **硬过滤**（不打分，直接剔除）：配料名含过敏原；痛风挡「水产」「汤品」；胃炎挡「微辣」；
- **一键拆成记录**（`Core/Recipes/RecipeServingPlanner`）：把 `recipe_ingredients` 的 name/amount/unit 逐条换算成克数 → 查成分库 → 写成多条记录。三条口径：
  1. `g` / `克` / `ml` / `毫升` 直取（液体按 1 ml ≈ 1 g，油 0.92 的差小于份量本身的估计误差）；其余单位借家用量词表折算（`一个鸡蛋 50 g`、`一根黄瓜 200 g`）；
  2. **折不出来就跳过，不拿 100 g 兜底**——「1 条鲈鱼」按 100 g 记，能量只有真实值的一成，当日汇总会静默偏低；
  3. **名字对不上也跳过**（`RecipeServingPlanner.Matches`）：搜索是含关键字就给，搜「蒜末」的第一条是「蒜末豆豉蒸鸡胸」，按配料记进去会带偏当日能量。判定规则：括注别名算同一物（`土豆` = `马铃薯(土豆)`）、多一两个字算同一物（`鸡胸肉` = `鸡胸脯肉`）、字数差到两倍就是另一道菜。
  跳过的项在提示里逐条点名（「M 项换算不了（…），请自己补」），不静默吞掉。
- 已知局限：标签只有「低GI / 糖尿病 / 减脂 / 健身 / 孕妇 / 老年人 / 高血压 / 清淡 / 蔬菜 / 汤品 / 水产 / 高蛋白 / 主食 / 肉类 / 微辣 / 均衡 / 家常菜 / 青少年 / 豆制品 / DHA」这些粗粒度词，没有「铁」「钙」「嘌呤」维度；表里也没有步骤与份量（一份是多少克），只能照菜谱自己的口径显示能量。

### 5.7 嘌呤分级（估算，非实测）

库里**没有**嘌呤字段，公开的成分表也只有几百种食物带嘌呤值。给 4 万多条食物硬凑一张嘌呤表，等于给 90% 的条目编数字——所以改成「类别基线 + 名称特征词」分级，实现在 `Core/Nutrition/PurineCatalog`：

| 级别 | 判定口径 | 界面文案 |
|---|---|---|
| 高 | 名称命中内脏（肝、腰、肚、肠、肺、心、胗、杂）、贝虾蟹蛤、浓汤/高汤/火锅底料、干制菌藻、啤酒、酵母、腐竹 | 「高嘌呤 · 150–1000 mg/100 g」，痛风/高尿酸「避免」 |
| 中 | 畜禽肉、水产、坚果；菌藻（鲜）、豆类（干豆） | 「中嘌呤 · 50–150 mg/100 g」，「缓解期限量」 |
| 低 | 蔬果、谷薯、蛋奶、油；豆腐/豆浆/豆花等湿豆制品 | 「低嘌呤 · < 50 mg/100 g」 |
| 未知 | 判不出来（加工食品、复合菜、名字里没有线索） | **不显示这一行** |

- 分级区间沿用《中国高尿酸血症与痛风诊疗指南》的常用切点（< 50 / 50–150 / 150–1000 mg/100 g）；
- **干制上调一级**：干香菇 214、鲜香菇 50，一个字差四倍，名称里带「干」时菌藻从「中」提到「高」；
- 名称命中后仍按类别收敛，避免单字误伤：「贝」会把「贝贝南瓜」判成海鲜，靠「蔬果优先」兜住；「素鸡」按豆制品给「中」而不是按「鸡」给「高」；
- 界面固定标注「按食物类别与名称估算，非逐条实测值」，不写成实测值；
- 已知误差：同一类里差别大的（猪脑 2,000+ vs 猪血 40）只能落在同一档；复合菜的嘌呤取决于配料比例，按名称基本判不出来，一律 `Unknown`。

### 5.8 草酸分级（估算，非实测）

草酸同样没有逐条实测值，沿用 5.7 的「类别基线 + 名称特征词」，实现在 `Core/Nutrition/OxalateCatalog`。切点取草酸钙结石膳食指导的通行口径：

| 级别 | 判定口径 | 界面文案 |
|---|---|---|
| 高 | 名称命中菠菜、甜菜、大黄、苋菜、竹笋/春笋/冬笋/笋干、马齿苋、香椿、欧芹；杏仁、腰果、芝麻；可可、巧克力、麦麸；茶叶与各类茶 | 「高草酸 · > 100 mg/100 g」，肾结石「限量或避免，焯水可去掉三到五成」 |
| 中 | 韭菜、秋葵、香菇、木耳、芦笋；红薯、土豆、芋头；花生、核桃等坚果；黄豆、黑豆、全谷物；茶汤、咖啡；内脏 | 「中草酸 · 25–100 mg/100 g」，「限量，并与含钙食物同餐」 |
| 低 | 肉禽鱼蛋奶、米面主食、瓜茄类、多数水果、油 | 「低草酸 · < 25 mg/100 g」 |
| 未知 | 判不出来（加工食品、复合菜、名字里没有线索） | **不显示这一行** |

- **基线不能照抄 5.7**：肉、水产、蛋、奶在嘌呤里是中高，在草酸里是低。草酸几乎只集中在植物性食物的少数几类（深绿叶菜的个别品种、根茎、坚果、可可、茶），照搬嘌呤的类别表会把整块肉判成高草酸；
- 名称特征比类别更可靠，所以顺序是「先排特例 → 再看名称 → 最后退类别」；
- **误判比漏判更糟**，专门留了 `Traps` 表收「名字带词、实际很低」的条目：莴笋（含「笋」）、杏仁豆腐、杏仁露、茶油、油茶、抹茶蛋糕、可可蛋糕。漏判只是少一条提醒，误判会让用户把一道普通菜永久划进禁区；
- 判不出高也不假装是低：`Unknown` 在详情页不占位、在规则里不触发，而不是给个「中」蒙过去；
- 已知误差：同名不同做法差别大（焯水后的菠菜草酸降三到五成，但库里只有「菠菜」一条）；复合菜按名称判不出来，一律 `Unknown`。界面固定标注「按食物类别与名称估算，非逐条实测值」。

## 六、检索策略

搜索走 `food.name_norm` / `py_full` / `py_initials` / `food_alias` 四个入口，**不使用 FTS5**：

> SQLite 的 `unicode61` 分词器会把一整串中文当成一个 token，搜「苹果」命中不了「红富士苹果」；`trigram` 分词器又要求关键词 ≥3 字符。而 `LIKE` 在 7,648 行（core）/ 44,688 行（full）上的全表扫描约 10–45 ms，行为可预测、无额外索引维护成本。

### 6.1 菜品名写法归一（2026-10-27）

同一道菜在不同来源里有不同写法：成分表写「番茄」，菜谱作者写「西红柿」；写「炒蛋」的人不会写成「炒鸡蛋」。`LIKE` 匹配对这种差异零容忍，用户只能换几个词再试，而他并不知道该换成什么。

做法是**给每条菜名生成等价写法，写进 `food_alias`**，检索链路一行都不用改：

| 项 | 口径 |
| --- | --- |
| 实现 | `tools/fooddb/dish_names.py`，在 `build_food_db.py` 里紧跟通用别名之后写入 |
| 替换单位 | 同义词组整词替换（番茄↔西红柿↔洋柿子、土豆↔马铃薯↔洋芋、芝士↔奶酪↔起司、鸡蛋↔蛋…共 26 组） |
| 步数 | 先替换一处，再在一处的基础上替换第二处（「西红柿炒鸡蛋」→「番茄炒蛋」要两步） |
| 上限 | 每条菜最多 8 个别名；两字以内的别名不写（「番茄」会命中上百道菜，结果全是弱相关，比搜不到更让人困惑） |
| 保护 | 「鸡蛋→蛋」遇到 蛋糕 / 蛋挞 / 蛋黄 / 蛋清 / 蛋白 / 皮蛋 / 咸蛋 / 松花蛋 / 蛋卷 就不替换，否则「鸡蛋糕」会变成「蛋糕」 |
| 不覆盖 | 别名与某条食物的正式名相同时跳过——库里真有一条「西红柿炒蛋」时，别名把它改指到「番茄炒蛋」等于藏起了那条数据 |
| 规模 | 全库 6,963 条，覆盖 3,598 道菜（core 库 25 条，菜品本就少） |

**只做同物替换，不做「近义」想象**：「生抽」和「老抽」都是酱油，但同一道菜里换掉会变味，不算同物；「地瓜」既可能指甘薯也可能指豆薯，也不收。误判比漏判更糟——用户会把一道普通菜永久划进禁区。

单测在 `tools/fooddb/test_dish_names.py`（`python tools/fooddb/test_dish_names.py`，11 条），检索链路的效果由 `FoodQueryRepositoryTests` 里两条针对真实库的用例钉住。

**排序权重**（`FoodSortMode.Relevance`）：

| 序 | 条件 | 意图 |
|---|---|---|
| 0 | `name_norm = 关键词` | 完全同名 |
| 1 | 命中 `food_alias` 代表条目 | 搜「苹果」时的「苹果(均值)」 |
| 2 | 与别名代表**同分类** | 都是水果，压过「苹果汁」「苹果丝瓜」 |
| 3 | 名称以关键词开头 | |
| 4 | 名称包含关键词 | |
| 5 | 拼音首字母开头 | |
| — | 依次按 `length(name)`、`-nutrient_count`、`name` | 名称越短越可能是主体食物 |

## 七、在线补录机制

`tools/fooddb/supplement_china.py`：

1. 取「同义词词表 + 常见食物词表」共 179 个词，逐个检查本地库是否已有名称或别名匹配；
2. 本地缺的，调中国营养学会平台 JSON 接口按关键词查询；
3. 取名称最贴近、营养项 ≥8 的一条，解析 36 列（能量列是 kJ，需 ÷4.184）；
4. 写入 `data/generated/china_supplement.json`；
5. `build_food_db.py` 读取该文件，以 `ds99` 身份合并进两个成分库，`food_id` 从 900000 起。

**当前结果**：179 个词本地缺失 **0** 个（补录前缺 11 个，其中 10 个由同义词解决，仅「火龙果」需要在线补录）。

**合规**：该平台声明数据限非商业用途，本项目只做**个人本地查询缓存**，界面标注来源并保留详情页外链。分发时如需商用，应先取得授权或移除 `ds99` 数据集。

## 八、扩展手册

### 新增一个数据集

1. 在源库 `source_dataset` 插入一行（含 `storage_allowed`、`import_status`，源库有触发器校验收录授权）；
2. 导入 `food` / `nutrient_definition` / `nutrient_value`；
3. 在 `nutrient_map.py` 加该数据集的 `*_MAP`（营养素）与 `GROUP_MAP`（分类）条目；
4. 在 `build_food_db.py` 的 `SOURCE_DISPLAY` 登记展示名与优先级，并决定是否加入 `FULL_DATASETS` / `CORE_DATASETS`；
5. 重跑 `python build_food_db.py --scope both`。

### 新增一个营养素

1. `nutrient_map.CANONICAL_NUTRIENTS` 追加一行 `(key, 中文名, 英文名, 单位, 分类, 排序, 参考日摄入量)`；
2. 各数据集的映射表指向该 key；
3. `NutriTrack.Core/Nutrition/NutrientKeys.cs` 同步加常量（两边必须一一对应）；
4. 重建库 → 运行 `dotnet test`（营养素目录数量断言会提醒是否同步）。

### 新增一个同义词

改 `tools/fooddb/synonyms.py`，按「通用名 → (候选名, ...)」追加，候选名**先用库里真实的规范名**（如 `鸡胸脯肉`），保留原词作为兜底。重建后 `[alias]` 行会打印解析结果与未解析清单。

### 重建全流程

```bash
python -m pip install pypinyin             # 必须有，否则拼音列全空
cd tools/fooddb
python build_food_db.py --scope both      # 生成 food_full.db / food_core.db（含 data/additional）
python link_china.py                      # 回填官方详情页链接（有缓存，不重复请求）
python link_china.py --db ../../data/generated/food_full.db
python supplement_china.py                # 仅当出现新的缺口词时才需要
python verify_build.py ../../data/generated/food_full.db   # 核对条数、来源、分类
```

重建会**直接删掉**旧库文件。改数据前先备份：`cp data/generated/food_full.db bak/food_full.db.$(date +%Y%m%d)`。

> 这两步 `link_china.py` 不能漏：`external_url` 是后处理写的，`build_food_db.py` 重建后该列全空，构建日志也不会有提示——只有详情页的「官方页面」按钮会静默消失。

## 九、已知局限

1. **同名跨源只保留一个代表**。`canonical_id` 让搜索结果干净，但详情页只能沿 `name_key` 看到**同名**的其他来源；异名同物（「菠菜」vs「菠菜[赤根菜]」）不会出现在「其他来源」里。
2. **`ref_daily` 是成人均值**，不能代表个体需求。个体化目标由 DRI 表按性别/年龄/孕期计算，两者用途不同，不要混用。
3. **营养值为每 100 g 可食部代表值**，不同产地、批次、烹调方式差异可达数倍。生熟状态必须在食物名里体现（库内已有 `(干)`、`(熟)` 等后缀）。
4. **别名覆盖率受限于词表**。给定 179 个词已全部覆盖，但词表外的通用名仍可能出现「搜不到理想条目」。
5. **在线补录是构建期行为**，运行时不联网补数据。若需要运行时补库，属于 W7 在线查询的职责。
6. **构建依赖 `pypinyin`**。缺了不会构建失败，但 `py_full` / `py_initials` 会全空，拼音搜索（`pg` 搜苹果）直接失效。构建结尾会打印「拼音 N 条」，N=0 即说明依赖缺失——早期版本这里是静默降级，产出的库功能残缺却看不出来。
7. **补充数据里的 40 条宏量不自洽未处理**。构建只是列出来供人工复核，没有自动修正，原因见 5.1 节。
8. **GI 覆盖率 2.4%**（1,054 / 43,071 代表行）。四源合并后比单源高得多，但 GI 表本身是「一项食物一个值」，无法外推到同类的其他品种（`西瓜(京欣一号)` 拿到值，`西瓜(无籽)` 没有）。界面上有值时显示分级色块，没值时不出 GI 徽标——不做「无数据也画个灰块」这种占位的假信息。
9. **GI 的产地/加工差异没体现**。同一碗米饭，籼米 82、粳米 90，煮得软烂还能更高；表里给的是实验条件下测得的代表值。GL 依赖库内碳水，碳水口径变了 GL 会跟着偏。
10. **嘌呤与草酸都是估算不是实测**。分级来自「类别 + 名称」，同一档里的个体差异（猪脑 2,000+ mg 与猪血 40 mg 都算「内脏」）体现不出来；复合菜、加工食品一律判 `Unknown` 并在界面隐藏，见 5.7 与 5.8。草酸尤其要注意「同一种菜不同做法」：焯过水的菠菜草酸降三到五成，库里只有「菠菜」一条，只能按生重给。
11. **Atwater 核算只是交叉校验，不改展示的标示能量**。4P+9F+4C 对含酒精与高纤食物必然偏离（啤酒差 63%、稻麸差 39%），构建期与运行时都只报告偏差、不修正数值，见 `Nutrition/Atwater.cs`。
